# CLI Command Reference

> All <!-- doc-count:cli-commands -->38<!-- /doc-count:cli-commands --> top-level `monomind` commands, verified against the `COMMAND_LOADERS` map in `packages/@monomind/cli/src/commands/index.ts` and against a live `monomind --help` and `monomind <command> --help` run on the built CLI (2.24.5). The category grouping is defined statically in `CATEGORY_NAMES` in the same file; real `Command` objects are attached on demand by `getCommandsByCategory()` and `loadAllCommands()`, with `getCommand`/`getCommandAsync` as the single-command entry points. Subcommand counts come from each command's own `subcommands:` array, not estimates.

**Note on `--help` coverage:** `monomind --help` lists every command in the table below except `report-crash`. That one is intentional: it is the only command with `hidden: true` (`report-crash.ts`), an internal command shelled out to by monotask/mono-clip crash handlers, not meant for interactive use. The table lists it anyway.

**Removed commands:** `monoswarm` and `autopilot` were removed in 2.22.0. Neither started an agent; both only recorded state files. Running either one prints what to use instead: Claude Code's Task tool, or `monomind org run <org>`. `monomind start` no longer takes `--topology`.

## Entry points

- Umbrella bin: `monomind` → `./bin/cli.js` (root `package.json` "bin"). CLI package bins: `monomindcli`, `cli`, `monomind` → `./bin/cli.js`, plus `monomind-mcp` → `./bin/mcp-server.js`. The `monomindcli` bin matches the package's own short name, which is what lets `npx -y @monoes/monomindcli@<version> mcp start` resolve an executable at all (#312, fixed in 2.14.0 — npx picks a bin only when exactly one exists or one matches the package short name).
- Run via `npx monomind@latest <cmd>`. Register as an MCP server with `claude mcp add monomind -- npx -y monomind@latest mcp start`.
- **MCP mode gate**: MCP server mode requires piped stdin AND either `mcp`/`mcp start` as argv, or the env var `MONOMIND_MCP_AUTODETECT=1` with zero args. Older versions treated any non-TTY invocation as an MCP server; that was removed as a privilege-escalation fix — plain non-interactive shell usage no longer risks silently starting an MCP server.
- `bin/cli.js` always reads its version from `package.json` at runtime — never hardcoded, so it can't drift from what's installed (confirmed live: `node bin/cli.js --help` reports the installed version). **Exception:** the separate `monomind-mcp` binary (`bin/mcp-server.js`) hardcodes `const VERSION = '3.0.0'` (`bin/mcp-server.js:13`) and reports it in its MCP `initialize` response (`:124`) regardless of the real installed version — a real version-drift bug specific to that one entry point.

## `doctor --component` categories (48)

`monomind doctor` (flags: `--fix`, `--install`, `--verbose`, `--json`, `--read-only`, `--offline`, `--component`) — `--component` accepts one of **48** named values, dispatched via the `componentMap` lookup table in `doctor.ts`. `monomind doctor --component bogus` prints the live list, which is the authority if this page drifts.

Several are aliases: `freshness` is `version`; `sidecars` is `appledouble`; `native-modules` is `native`; `doc-extractors` is `documents`; `decision` is `jev`; `dashboard-token` is `monoes-token`. The `-c` help string names only 37 of the 48 and has drifted from the table; trust the table.

**What the newer checks report**

- `cost-settings` ("Token Cost Settings", 2.24.4): read-only. It reads `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json` and the process environment and warns about settings that multiply token use: `CLAUDE_CODE_EFFORT_LEVEL` overriding `effortLevel`, a `CLAUDE_CODE_AUTO_COMPACT_WINDOW` above 400,000, `CLAUDE_CODE_MAX_OUTPUT_TOKENS` above 64,000, `ENABLE_TOOL_SEARCH=false`, and the same hook helper and argument registered twice. It names the file and key and edits nothing. A leftover `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` or `monomind.agentTeams` block is a note, not a warning, and points at `monomind init upgrade --settings` to remove it.
- `mcp-running` ("MCP Server Version", `doctor-pick-checks.ts`): warns when a live `monomind ... mcp start` process for this project resolves to a CLI package other than the one now installed, or that package was replaced after the process started. This is Claude Code holding an MCP server open across a CLI upgrade, so the hooks suggest tools the running server lacks (such as `org_skill_show`). It infers the version from the resolved script's package and mtime, since there is no RPC to ask the process; only servers whose working directory is this project (or unknown) count, and it is skipped on Windows. It stands alone from the registry-only `mcp` check, which starts nothing.
- `claude-runtime` ("Claude runtime"): which Claude Code binary the Claude runtime uses and why others were skipped (`--claude-path`, `MONOMIND_CLAUDE_PATH`, `claude.path`, then the system install).
- `agent-runtimes` ("Agent runtime readiness"): lists installed runtimes whose automation is unavailable and the reason (for example `freebuff`: no headless transport; `kilo`: full access only, which a sections org refuses). It checks presence only and never runs a vendor CLI.
- `org-skills`: lists the org skills that come from the project's or the user's library rather than the bundled one, which decide MCP tools the org daemon grants (informational), and warns when `.mcp.json` servers are approved by name but `.mcp.json` is missing, untracked or modified.
- `hook-monograph`: fails when the monograph index is more than 50 commits behind and the hooks cannot rebuild it, naming a missing `@monoes/monograph` package or an unbuilt `better-sqlite3`.
- `catalog`: checks catalog store and state consistency.
- `jev`: `doctor -c jev` probes each configured Jev provider (network).

**`--json`, `--read-only`, `--offline`.** `--json` puts one JSON document on stdout (human text goes to stderr) with every check's result, the `component` id that re-runs it, and how its fix is applied. `--json` implies `--read-only` unless you add `--fix` or `--install`: a read-only run changes no file in the project or `$HOME` (no fixes, no registry refresh, no update check). `--offline` skips the checks that use the network and reports them as skipped. The "update available" notice goes to stderr, so it never lands ahead of the JSON.

**Default sweep versus `-c`.** A plain `monomind doctor` runs its own `alwaysOnChecks` and `codeOnlyChecks` arrays in `doctor.ts`, not the 48-value list.

- Always on: version, node, npm, claude, claude-runtime, agent-runtimes, config, project-root, memory, disk, monograph, memory-pkg, helpers, monoes, gates, hook-settings, registry, git, api, memory-proficiency, metrics-freshness, security-audit, second-brain, kg, appledouble, documents, jev, crash-reporting, cost-settings, org-skills.
- Added for code projects only (the capability fingerprint puts code confidence at 0.1 or more): git-repo, native, mcp, mcp-running, typescript, graph-freshness, hook-monograph, gitignore, monoes-token, platforms.
- Never in the default sweep, only with `-c`: `monoes-tools`, `catalog` and `pick`. `git-repo` is a sweep id only and is not a valid `-c` value.

`pick` (`doctor-pick-checks.ts`) is one row on agent/skill picking: registry agent count, duplicates and staleness, skill index freshness and counts (platform/org/user), whether a decision model is configured (no probe), the keyword score on the frozen `tests/pick-eval` set when the project carries one, and [PICK] adherence from `.monomind/route-outcomes.jsonl` and `.monomind/pick-adherence.jsonl`, plus subagent success when the pick was followed versus overridden (`.monomind/pick-stats.json`). It rebuilds stale indexes and scores the eval set, so it stays opt-in. `jev` differs: a bare `monomind doctor` always runs `checkDecisionModelIfConfigured()` (config-only, no network — silent unless Jev env is set), while `doctor -c jev` runs the network-probing flavor instead. `doctor -c mcp` starts the configured server and verifies it answers `initialize`; the default run's `mcp` check only reads the registry.

## Crash reporting

`packages/@monomind/cli/src/services/crash-reporter.ts` is shared across the monoes tool family — `monotask` and `mono-clip` shell out to `monomind report-crash`. You're asked **once**, the first time an interactive crash happens — the local report path is shown before asking, and the default answer is No. Until you've answered, a non-interactive crash (CI, agents — most real runs) never asks and only saves locally. Once you've explicitly chosen — via the prompt or `monomind crash-reporting enable`/`disable` — that answer is used every time, interactive or not; `monomind doctor` shows the current state (on/off/unanswered). Reports are secret/PII-scrubbed before filing, deduplicated by a sha1 signature of repo+normalized title within a dedup window, and rate-limited per repo (statuses: `created`, `duplicate`, `saved-locally`, `disabled`, `rate-limited`, `error`).

## Input validation

Former `@monomind/security` package is gone — input validation now lives inline at `packages/@monomind/cli/src/utils/input-guards.ts`, with a single typed `validateInput()` entry point covering string/number/path/url/orgName types plus a heuristic prompt-injection detector for untrusted external content.
