# Monomind — Project Milestones

A full-monorepo review, package by package: what's actually shipped ("Achieved Milestones," verified against the real source/docs/tests) and what's worth doing next ("Future Milestones," each carrying an impact score). This is an ideation stepping stone, not a committed roadmap — add, re-score, and prune freely.

**Revision 5 (2026-09-16, 02:40 CEST).** Revisions 1–2 inventoried and scored; revision 3 (loop round 1) added the Monoswarm and Dashboard sections; revision 4 (round 2) covered runners, resume, accounting, content, and the knowledge layer. This revision is round 3: CLI UX and error messages measured across all 36 command groups, the documentation site and every documented command snippet, dependency health and upgrade risk, concurrency experiments, and the per-session cost of the default MCP roster. It adds ~35 items, five of them 8/10 (silent success on unknown subcommands/flags, a dead hardened MCP loop, an EOL Node floor, a docs site that can't reach the docs, and `@monoes/memory` failing under any write concurrency), and verifies one hypothesis as sound (monograph reads during a build).

## How to read the scores

Every future item starts with `[N/10]` — **impact on users and on the project's core promise**, not effort. `(quick win)` marks items that look like under a day of work.

| Score | Meaning |
|---|---|
| **10** | Fixes something currently broken or unsafe for most users, or unlocks the core promise |
| **8–9** | Major capability, reliability, or trust gain for a large share of users |
| **6–7** | Solid improvement with moderate reach, or high value at low effort |
| **4–5** | Nice-to-have, niche audience, or hygiene with some user-visible benefit |
| **1–3** | Cosmetic / internal tidiness, low user impact |
| **0** | Not worth doing or unsupported by evidence → removed |

## monomind (umbrella) (`monomind` v2.10.30)

`monomind` is the umbrella package published on npm — a pure forwarding shim over `@monoes/monomindcli` (deliberately code-free after a ~27 MB double-publish incident). The repo root also hosts the pnpm workspace, release/version-integrity scripts, CI workflows, the dependency policy, the crash reporter's entry point, and the documentation (`README.md`, `doc/` deployed to GitHub Pages, 17 concept docs).

### Achieved Milestones
- Umbrella/CLI split with a resolution shim robust across nested, hoisted, global, and pnpm-linked layouts; lockstep version + double-publish prevention (`scripts/check-publish-versions.mjs`); doc-count drift automation for two counters; git hooks auto-activation in-repo.
- Three-workflow CI suite (`tests.yml` root + 9-package Linux + 5-package Windows matrix; `publish-smoke-test.yml` with a 4-case behaviour suite; `pages.yml`). No lint, typecheck, coverage, link-check, or license gate.
- Dependency health (round 3): 0 deprecated direct deps (71 checked); `pnpm audit` 0 vulnerabilities across 542 deps; no copyleft blockers in the 293-package prod tree (LGPL libvips via sharp is dynamically linked; `jszip` dual-licensed); all 23 CLI optional deps are loaded lazily; the three ignored build scripts (`esbuild`, `onnxruntime-node`, `puppeteer`) are verified harmless; `typescript` 7.0.2 (native) is current.
- Outbound egress audited: code, documents, memory, and prompts stay local unless the user configures a provider or clicks "Upload org"; default-on egress is the 24 h-throttled npm update check, `doctor`'s `npm view`, and the crash reporter.
- The README quickstart works end to end in a scratch project (`init` → `mcp verify` 67 tools 3/3 → `doctor --fix` 24 pass → `org run sample-team --dry-run` → `doc ingest`/`doc search` → `memory store`); 158 of 160 documented command names exist; the last 5 CHANGELOG entries are accurate and candid.
- Active release cadence; backlog 8 open / 176 closed; the 7 external reports cluster on generated hooks breaking the host session and install breakage.

## Org Runtime v2 (part of `@monoes/monomindcli`)

Org Runtime v2 is a daemon-coordinated system for running autonomous multi-agent "organizations" — role-based teams of live, provider-backed AI sessions (a boss plus specialist roles) that communicate over async mailboxes, persist resumable state via checkpoints, and can be driven by interchangeable LLM backends, with fault tolerance, cross-org/cross-process messaging, and a full audit trail (`bus.jsonl`).

### Achieved Milestones
- `OrgDaemon` lifecycle (`orgrt/daemon.ts`, ~1076 lines): `startOrg`/`stopOrg`/`deliver`/`resumeOrg`, lazy role spawning, atomic `spawning` guard; `respawnRole` guarded by `running.respawning` + `slot.respawnPromise` (verified race-free, round 3).
- 14 runtime ids over 14 files (`agent-runner.ts` = Claude SDK, plus 13 `*-runner.ts`). Per the round-2 matrix: `maxTurns` honored by claude and vercel only; provider-session resume for 8 runners, not for 6 (copilot, crush, pi, pi-rpc, qwen-rpc, hermes); usage/cost real for 6 of 14 (copilot and crush report zero, grok's field names are guessed, kimicode's come from a timestamp-filtered wire file).
- "Fence Protocol" (`tool-fence.ts`) for the 12 runners without native tool-calling; `MAX_TOOL_ROUNDS` = 10.
- Per-role provider/runtime resolution (role > org > `MONOMIND_RUNTIME`), mixed-runtime orgs.
- Checkpoint/resume: captured on stop/crash only; every `runtime.json` write is tmp+rename; v1→v2 migration, checksum and unknown-version validation tested. Survives resume: unconsumed mailbox queues, usage incl. retired usage, generations/respawn counts, role overrides, the task DAG, gates and `ask_human` questions. Doesn't: the in-flight message, worktrees, pending approvals, conversation state on 6 runners.
- Four workspace isolation modes; per-role `PolicyEngine` enforced through the Claude SDK `canUseTool` hook only.
- Fault tolerance: bounded boss restarts, per-role circuit breaker, idle watchdog, stale-PID detection, serve lock, atomic `runtime.json`, orphan SDK reaping. `Mailbox` push/shift has no await between check and mutate (verified); broker registry writes are tmp+pid+rename with 90 s staleness (verified).
- Cross-org/cross-process messaging (mailboxes, HTTP broker, offline queuing, `autoWake()`, `org inbox` for SSH delivery); `ask_human`, `org_gate`, `org_task*` DAG, `OrgScheduler`; org-scoped KG memory; ~130+ role skill prompts.
- Tests: every runner has a dedicated test file (parser-fixture and fake-child tests; none exercise real subprocess semantics); 60+ orgrt test files; no fake runner exists.

### Future Milestones
- **[9/10]** Enforce role policy on subprocess runners — and stop leaking the daemon's environment into them. `PolicyEngine.decide()` runs only through the SDK `canUseTool` hook; the Codex runner launches with sandbox mode `danger-full-access` (`codex-runner.ts:392`), Antigravity passes its permission-bypass flag (`:367`), Qwen `--yolo` (`:346`). `resolveProviderEnv` starts from a full copy of `process.env` (`provider.ts:14-17`) and every runner spreads `{...process.env, ...args.env}` again — a Codex role runs with `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GITHUB_TOKEN`, `AWS_*` and an unsandboxed shell. Map policy → native sandbox flags where supported, OS sandbox otherwise; child env from an allowlist (`passEnv` in `RUNNER_SPECS` + role `env_passthrough`); `org validate` warns and `org run` requires `--accept-unsandboxed`; enforcement matrix; scrub-on-spawn test per runner.
