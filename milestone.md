A full-monorepo review, package by package: what's actually shipped ("Achieved Milestones," verified against the real source/docs/tests) and what's worth doing next ("Future Milestones," each carrying an impact score). This is an ideation stepping stone, not a committed roadmap — add, re-score, and prune freely.

**Revision 6 — final revision of the overnight loop (2026-09-16, 06:15 CEST).** Six revisions, ~45 agents, five review rounds. This revision applies a whole-document calibration pass (scores made consistent across sections; 16 duplicate groups merged into canonical homes; weak-evidence items demoted), adds round 4's findings (the build script that doesn't build the product, `init` re-prefixing its own output, four reproduced at-rest/federation security defects), and corrects the former headline item's reach. Two caveats: (1) rounds 1–3's *runtime* measurements through `node bin/cli.js` ran against a CLI `dist` built on 2026-09-09, because the root `pnpm build` never builds the CLI package (see umbrella); every file:line claim was made against current source. (2) Five lenses never delivered their reports and are not reflected here: session-start-chain and dashboard performance, monobrowse/monodesign end-to-end runs, a README promise-by-promise audit, cross-platform (macOS/Windows) static analysis beyond the known CI gap, and an evaluation of whether monograph's `suggest`/`impact`/`context` answers beat plain grep on real tasks. Those are the next rounds to run.

## How to read the scores

Every future item starts with `[N/10]` — **impact on users and on the project's core promise**, not effort. `(quick win)` marks items that look like under a day of work.

| Score | Meaning |
|---|---|
| **10** | Fixes something currently broken or unsafe for most users, or unlocks the core promise |
| **8–9** | Major capability, reliability, or trust gain for a large share of users |
| **6–7** | Solid improvement with moderate reach, or high value at low effort |
| **4–5** | Nice-to-have, niche audience, or hygiene with some user-visible benefit |
| **1–3** | Cosmetic / internal tidiness, low user impact |
| **0** | Not worth doing or unsupported by evidence → removed |

## Top 10 for a real user of `npx monomind init` + Claude Code

1. **Hook enrichment never reaches the model** — the graph-first promise is undelivered in every session (`MONOMIND_HOOK_QUIET=1`, plain stdout on tool hooks).
2. **better-sqlite3 ABI failures and the EOL Node floor** — when install fails, nothing works (#231 and four siblings); the floor and the ABI story are one decision.
3. **The dead hardened MCP loop** — on the loop `.mcp.json` actually runs, every tool result is double-wrapped, `isError` is lost, payloads are 9–27% larger.
4. **Phantom references and the generated CLAUDE.md** — 42 nonexistent tools, 4 nonexistent CLI groups, 38 phantom routing agents, `init --wizard`, "MUST init monoswarm": the model burns turns every session on instructions that can't work.
5. **Everything is persisted verbatim, and it's committable** — the default hooks write every Bash command, Write body, and prompt to disk unredacted at 0644, and init's generated `.gitignore` leaves those stores (plus the dashboard token and org scrollback) committable.
6. **Crash reporter files public GitHub issues under the user's identity, by default.**
7. **Cost understated ~3×** — the number every user reads is wrong and says nothing about it.
8. **`config_set` silently deletes provider API keys** — data loss from a default-exposed tool.
9. **Unknown subcommands and flags exit 0** — agents "succeed" doing nothing; scripts can't trust exit codes.
10. **`@monoes/memory` fails under the concurrency a normal session already produces**, and swallows the failures.

## First three PRs (twelve quick wins, grouped by file locality)

**PR 1 — Hooks that help and tell the truth** (`.claude/helpers/handlers/capture-handler.cjs`, `helpers/utils/monograph.cjs`, `helpers/statusline.cjs`, `helpers/handlers/route-handler.cjs`, `helpers/event-logger.cjs`, `src/init/settings-generator.ts`, `src/init/write-runtime-config.ts`): `.unref()` the 3 s timer + a < 200 ms latency test; drop `MONOMIND_HOOK_QUIET` and emit `hookSpecificOutput.additionalContext` from tool hooks; statusline counts only real graph calls and reads Claude Code's stdin for model/cost; redact tool inputs in the event log and drop the `raw` field; generate the same `.monomind/.gitignore` the repo itself uses. *Effect:* subagent hooks stop stalling, graph hints reach the model, the statusline shows the real model and cost, secrets stop landing in committable logs.

**PR 3 — The CLI and the build mean what they say** (`src/commands/index.ts`, `parser.ts`, `suggest.ts`, `pricing/model-pricing.ts` + its three copies, `services/crash-reporter.ts`, root `package.json`, `packages/@monomind/memory/src/sql-driver.ts`, `memory-bridge.ts`, `orgrt/remote.ts`): reject unknown subcommands/flags (exit 2, suggestion on stderr); one pricing table with fable-5/5.1 rows and an `unpriced` marker; crash reporter prompts once on a TTY; `pnpm build` builds the CLI; `tx.immediate()` + bounded `SQLITE_BUSY` retry; stopword-free coverage gate; SSH payload on stdin. *Effect:* typos fail loudly, cost numbers stop being 3× low, nothing is filed to GitHub without consent, the build builds the product, memory writes stop failing, federated hosts can't be commanded by a prompt-injected role.

## monomind (umbrella) (`monomind` v2.10.30)

`monomind` is the umbrella package published on npm — a pure forwarding shim over `@monoes/monomindcli` (deliberately code-free after a ~27 MB double-publish incident). The repo root also hosts the pnpm workspace, the build and release scripts, CI workflows, the dependency policy, the crash reporter's entry point, and the documentation (now its own section).

### Achieved Milestones
- Umbrella/CLI split with a resolution shim robust across nested, hoisted, global, and pnpm-linked layouts; lockstep version + double-publish prevention (`scripts/check-publish-versions.mjs`); doc-count drift automation for two counters; git hooks auto-activation in-repo (the activated `commit-msg` hook is inert — see Future).
- Build and test are fast on TypeScript 7 (native): root `pnpm build` 1.9 s, CLI package build 0.9 s, `tsc --noEmit` 0.25 s; the full test set passes on main — routing 98, hooks 64, memory 125 (+46 skipped), mcp 106, monofence 136, monobrowse 249, root `tests/` 1,151 (38 s), CLI 3,052 tests (60 s). No failing test on main.
- Three-workflow CI suite (`tests.yml` root + 9-package Linux + 5-package Windows matrix; `publish-smoke-test.yml` with a 4-case behaviour suite; `pages.yml`). No lint, typecheck, coverage, link-check, snippet, license, or size gate.
- Dependency health: 0 deprecated direct deps (71 checked); `pnpm audit` 0 vulnerabilities across 542 deps; no copyleft blockers in the 293-package prod tree; all 23 CLI optional deps loaded lazily; the three ignored build scripts verified harmless.
- Outbound egress audited: code, documents, memory, and prompts stay local unless the user configures a provider or clicks "Upload org"; default-on egress is the 24 h-throttled npm update check, `doctor`'s `npm view`, and the crash reporter.
- Active release cadence; backlog 8 open / 176 closed; the 7 external reports cluster on generated hooks breaking the host session and install breakage.

## Org Runtime v2 (part of `@monoes/monomindcli`)

Org Runtime v2 is a daemon-coordinated system for running autonomous multi-agent "organizations" — role-based teams of live, provider-backed AI sessions (a boss plus specialist roles) that communicate over async mailboxes, persist resumable state via checkpoints, and can be driven by interchangeable LLM backends, with fault tolerance, cross-org/cross-process messaging, and a full audit trail (`bus.jsonl`). Calibration note: most items here affect only org-runtime users on non-Claude runners — a small share of the base — and are scored accordingly.

### Achieved Milestones
- `OrgDaemon` lifecycle (~1076 lines): start/stop/deliver/resume, lazy role spawning, atomic `spawning` guard; `respawnRole` and `Mailbox` push/shift verified race-free.
- 14 runtime ids over 14 files (Claude SDK + 13 subprocess/SDK runners). Per the round-2 matrix: `maxTurns` honored by claude and vercel only; provider-session resume for 8 runners, not for 6; usage/cost real for 6 of 14.
- "Fence Protocol" (`tool-fence.ts`) for the 12 runners without native tool-calling; per-role provider/runtime resolution; mixed-runtime orgs.
- Checkpoint/resume: captured on stop/crash only; atomic `runtime.json` writes; v1→v2 migration and validation tested. Survives resume: unconsumed mailbox queues, usage incl. retired usage, generations, role overrides, the task DAG, gates and questions. Doesn't: the in-flight message, worktrees, pending approvals, conversation state on 6 runners.
- Per-role `PolicyEngine` enforced through the Claude SDK `canUseTool` hook only. Fault tolerance: bounded boss restarts, circuit breaker, idle watchdog, stale-PID detection, serve lock, orphan SDK reaping. Cross-org/cross-process messaging with sender-identity verification on `xdeliver` (`cross-org.ts:598-608`); bus `audit` events redact and truncate tool inputs; SSH `BatchMode=yes` fails closed on unknown hosts.
- Tests: every runner has a dedicated (fake-child/fixture) test file; 60+ orgrt test files; no fake runner exists.

### Future Milestones
- **[8/10]** (quick win) SSH federation interpolates agent-authored message bodies into a *remote* shell string. `remote.ts:65-68` builds `` `cd ${JSON.stringify(host.cwd)} && npx monomind org inbox ${orgName} --json ${JSON.stringify(payload)}` `` as one argv to local `ssh` (the local shell was fixed in SEC-4), but sshd hands it to the remote login shell, which expands `$(…)`, backticks, and `$VAR` inside double quotes — `JSON.stringify` escapes none of them (verified). `body` is a role's LLM output (`cross-org.ts:268-278`), so a prompt-injected role gets command execution on the federated host as the SSH user; `orgName` is unquoted; `host.cwd` same class.
