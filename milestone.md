# Monomind — Project Milestones

A full-monorepo review, package by package: what's actually shipped ("Achieved Milestones," verified against the real source/docs/tests) and what's worth doing next ("Future Milestones," each carrying an impact score). This is an ideation stepping stone, not a committed roadmap — add, re-score, and prune freely.

**Revision 2 (2026-09-15).** Revision 1 was a 13-agent inventory. This revision re-verified every future item against the code with a 10-agent swarm (4 critique agents, 6 fresh lenses: GitHub backlog, tests/CI, security, measured performance, reliability, DX/doc drift). 24 items were removed as wrong, already done, or not actionable (listed at the end); ~55 were reworded with corrected evidence; ~45 new items were added. Several first-revision "Achieved" claims were also corrected.

## How to read the scores

Every future item starts with `[N/10]` — **impact on users and on the project's core promise**, not effort. `(quick win)` marks items that look like under a day of work.

| Score | Meaning |
|---|---|
| **10** | Fixes something currently broken or unsafe for most users, or unlocks the core promise |
| **8–9** | Major capability, reliability, or trust gain for a large share of users |
| **6–7** | Solid improvement with moderate reach, or high value at low effort |
| **4–5** | Nice-to-have, niche audience, or hygiene with some user-visible benefit |
| **1–3** | Cosmetic / internal tidiness, low user impact |
| **0** | Not worth doing or unsupported by evidence → removed |

## monomind (umbrella) (`monomind` v2.10.30)

`monomind` is the umbrella package published on npm — the thing `npm install -g monomind` actually installs. It ships zero code of its own: `bin/cli.js` is a pure forwarding shim that locates `@monoes/monomindcli` (the real CLI, in `packages/@monomind/cli`) on disk via `require.resolve.paths()` and `import()`s its bin. It's deliberately structured this way because publishing the CLI payload from both packages once caused a ~27 MB double-publish and a two-package version lockstep bug — the shim's own header comment documents the incident as the reason it must stay code-free. The repo root also hosts all repo-wide tooling: the pnpm workspace definition, release/version-integrity scripts, CI workflows, and top-level docs (README, CHANGELOG, LICENSE).

### Achieved Milestones
- Umbrella/CLI split with a dependency-resolution shim (`bin/cli.js`) robust across nested, hoisted, global, and pnpm-linked `node_modules` layouts, and against the CLI's `exports` map gating (falls back to filesystem resolution rather than `require.resolve()` on the package specifier, since older published CLI versions reject that).
- Lockstep version + double-publish prevention via `scripts/check-publish-versions.mjs`, run as `prepublishOnly`: enforces root version == CLI version, enforces the `workspace:*` protocol on the CLI dependency pin, blocks `npm publish` in favor of `pnpm publish` (npm can't rewrite `workspace:*`), and catches npm's `overrides`-vs-direct-dependency conflict (`EOVERRIDE`) before it surfaces for end users.
- Doc-count drift automation (`scripts/generate-doc-counts.mjs`) substitutes computed counts into `<!-- doc-count:NAME -->` markers across README/CLAUDE.md/doc/* with a `--check` mode wired into CI/prepublish — but it only tracks two counters (`workers`, `root-skills`); the headline figures in CLAUDE.md ("29 hook subcommands", "8 background workers", "66+ tools") are unmarked and currently wrong or unverified (see Cross-Cutting §9).
- Git hooks auto-activation (`scripts/install-hooks.mjs`, run via `prepare`) points `core.hooksPath` at `.githooks/` (`pre-commit` secret scanning, `commit-msg`) — inside this repo only.
- Three-workflow CI suite: `tests.yml` runs a root job plus a 9-package Linux matrix and a 5-package Windows matrix (each Windows gap documented rather than silently skipped); `publish-smoke-test.yml` does pre-publish tarball-install smoke tests, post-publish registry smoke tests (daily cron), and a 4-case "published behaviour" regression suite; `pages.yml` deploys `doc/` to GitHub Pages. There is no lint, typecheck, or coverage gate in any workflow.
- pnpm workspace spans `packages`, `packages/@monomind/*`, `packages/@monoes/*`, `packages/plugins/*`, and `packages/monofence-ai`, with root-level `overrides` (28 security-driven version floors) and `onlyBuiltDependencies` scoping native builds to tree-sitter/better-sqlite3. `pnpm audit`: 0 vulnerabilities across 542 dependencies.
- `doc/concepts/` holds 17 concept docs (antigravity, codex, documents-dashboard, hooks, kimicode, local-llm-providers, mcp-server, memory, monobrowse, monodesign, monograph, monoswarm, opencode, org-runtime, routing, security, statusline); 10 of them carry stale per-doc version pins and 7 have none.
- Apache 2.0 licensed (confirmed in `LICENSE`).
- CHANGELOG (1300+ lines) shows an active, fast-moving release cadence with recognizable eras: 2.2.0 baseline (Org Runtime v2 SDK daemon), 2.8–2.9 "comprehensive review-fix" releases driven by multi-agent review swarms (2.9.0: 7-agent swarm found/fixed 28 issues in one release), and the current 2.10.x stream focused on agent-runner robustness and `doctor`/diagnostics accuracy.
- Backlog snapshot (2026-09-15): 8 open / 176 closed issues, 59 PRs. 177 of 184 issues are maintainer-filed; the 7 external reports cluster entirely on two themes — generated hooks breaking the host session, and install/native-module breakage.

## Org Runtime v2 (part of `@monoes/monomindcli`)

Org Runtime v2 is a daemon-coordinated system for running autonomous multi-agent "organizations" — role-based teams of live, provider-backed AI sessions (a boss plus specialist roles) that communicate over async mailboxes, persist resumable state via checkpoints, and can be driven by interchangeable LLM backends. It exists to let a single `monomind org` config file describe a durable, budget-bounded, human-supervisable agent team rather than a one-shot scripted agent loop — with fault tolerance (crash/restart, idle watchdog, circuit breakers), cross-org and cross-process messaging, and a full audit trail (`bus.jsonl`) for every message, tool call, and state transition.

### Achieved Milestones
- `OrgDaemon` lifecycle (`orgrt/daemon.ts`, ~1076 lines) covering `startOrg`/`stopOrg`/`deliver`/`resumeOrg`, with lazy role spawning (boss spawns immediately, specialists spawn on first mailbox message) and an atomic `spawning` guard against duplicate spawns.
- 13 `AgentRunner` backend files behind one interface: Claude (default, `@anthropic-ai/claude-agent-sdk`), Opencode, KimiCode, Codex (ChatGPT subscription), Antigravity (Google AI Pro/Ultra), Vercel AI SDK (15 vendors incl. Gemini via `google`, + OpenAI-compatible escape hatch), plus Hermes, Copilot, Crush, Grok, Qwen (+RPC) and Pi (+RPC). Six are documented in `org-runtime.md`; seven are not.
- A "Fence Protocol" (`tool-fence.ts`) that renders org tools as markdown in the system prompt and parses tool calls back out of plain assistant text for runners without native tool-calling, including tolerant parsing of malformed trailing JSON.
- Per-role provider/runtime resolution with three-level precedence (role `runtime` > org-level `runtime` > `MONOMIND_RUNTIME` env), enabling mixed-runtime orgs (e.g., a Claude coordinator delegating to opencode workers).
- Checkpoint/resume system (`checkpoint.ts`, `checkpoint-ops.ts`) with 24h TTL, checksum validation, per-role mailbox queues, token/cost tracking, session IDs, and a bounded scrollback ring buffer (500-line default) restored on resume — captured on stop/crash only (see Future).
- Four workspace isolation modes: `repo`, `isolated`, `worktree`, and `worktree-per-role` (one `git worktree add --detach` per non-boss role), all cleaned up on stop.
- Per-role `PolicyEngine` (tool allow/deny lists, file read/write glob scopes with realpath symlink handling, web-domain allowlists, per-role token budgets, git access levels `none`/`read`/`commit`/`push`) — enforced through the Claude SDK `canUseTool` hook (`session.ts:586`, `policy.ts:206-260`). **For subprocess runners it only covers in-process org tools; the child CLI's native file/shell/web tools are not policed** (see Future).
- Fault tolerance: boss crash recovery with bounded restarts (`MAX_BOSS_RESTARTS=2`, backoff `[10s, 30s]`); configurable `circuit_breaker` that trips a role's mailbox after N consecutive session failures; idle watchdog (default 10 min, up to 3 nudges before stop); stale-PID detection (`org.ts:668-720`), serve lock (`org.ts:1218`), atomic `runtime.json`, orphan SDK reaping (`daemon.ts:1064`).
- `OrgBus` append-only JSONL event log with in-process fan-out across 10 event types plus disk replay via `readHistory()`; `StateDetector` infers live per-role activity from the raw SDK message stream.
- Cross-org and cross-process messaging: intra-org mailbox delivery, in-process cross-org lookup, HTTP broker-based cross-process delivery (`broker.ts`, filesystem registry with 20 s heartbeat / 90 s staleness, 0o600 files), offline queuing with `autoWake()`, and an `org inbox` subcommand (`org.ts:2337-2366`, commit 3c704d81d) that `remote.ts:66` shells to over SSH for federated delivery.
- Human-in-the-loop primitives: `ask_human` tool with live/offline-queued answer delivery, and `org_gate` hard-blocking approval checkpoints for irreversible actions.
- `org_task`/`org_task_done`/`org_tasks` dependency-DAG task tracking (`task-dag.ts`) with auto-dispatch of ready tasks; `OrgScheduler` for `org serve` scheduled runs (`"15m"/"2h"/"45s"`), with catch-up-run coalescing.
- Cross-run knowledge-graph memory per org (`org_recall`/`org_remember`/`org_learn`, org-scoped via `KgScope`) plus optional Second Brain `knowledge_search` integration; ~130+ predefined role skill prompts under `orgrt/role-skills/`.
- 60+ test files in `__tests__/orgrt/` — broad on daemon/checkpoint/budget/mailbox/circuit-breaker/scheduler, thin per runner (11 of 14 runners have ≤ 3 referencing test files).

### Future Milestones
- **[9/10]** Enforce role policy on subprocess runners. `PolicyEngine.decide()` runs only through the SDK `canUseTool` hook; the Codex runner launches with sandbox mode `danger-full-access` (`codex-runner.ts:392`), the Antigravity runner passes its permission-bypass flag (`antigravity-runner.ts:367`), the Qwen runner passes `--yolo` (`qwen-runner.ts:346`) — so a role with `fileWrite: ['src/**']` and an empty `webAllow` gets full disk and network on those backends while the docs advertise glob scopes and domain allowlists. Plan: map policy → native sandbox flags where the CLI supports them (codex `--sandbox workspace-write`, add-dir lists, allowed-tools), run the child under an OS sandbox (bubblewrap / `sandbox-exec` / firejail, or at minimum a dedicated workdir + env scrub) otherwise, make `org validate` warn and `org run` require `--accept-unsandboxed` when a role's policy is narrower than its runner can enforce, and publish an enforcement matrix per runner.
- **[7/10]** Liveness regression harness. The largest closed-issue cluster (~45: idle watchdog #168/#173/#175/#183/#194, approvals #135/#160/#213/#214, resume #140/#149; #204 alone took 13 commits; external #25: whole org dies when one agent hits `max_turns`) keeps re-breaking. Build `org run --simulate` with a fake runner that asserts the three invariants (productive work continues / only real blockers stop work / no infinite loop) and run it in CI on every orgrt change; add one parameterized runner contract test (stream chunk parsing, exit-code → status mapping, `includePartialMessages` gating, abort) with fake timers — 4 of the last 5 flake fixes were orgrt timing.
- **[6/10]** (quick win) `run_config.prechecks` only execute for `org serve` (sole caller `org.ts:1354` inside `serveAction`); `org run` never runs them — wire `runPrechecks` into the run path. Separately, `stale_base_threshold` promises "warn or refuse to start" (`daemon.ts:1072`) but can only emit an audit bus event.
- **[6/10]** Periodic checkpoints and bus rotation. `captureCheckpoint` is called only on stop/crash (`daemon.ts:2158, 2356, 2398`), so a SIGKILL/OOM/power loss leaves nothing to resume from — exactly the runs that need it. `bus.jsonl` is append-only forever (`bus.ts:27-70`) and `reporting.ts`/`checkpoint-ops.ts` read the whole file. Add a debounced periodic checkpoint (every N bus events or 60 s, atomic write) and a segmented bus (`bus.0001.jsonl`, roll at ~50 MB) with readers iterating segments.
- **[6/10]** (quick win) `org validate` checks schema only (`org-observe.ts:44`); make it call the existing `scanInstalled()` preflight (`runner-registry.ts:369`, already used by `agent exec scan`) for each role's resolved runtime so missing binaries/optional deps surface before `org run`. Pair it with a per-runner verification ledger in `org-runtime.md` (live-tested version, date, known gaps) — open #178/#181/#242/#243 exist because users can't tell which runtimes are actually verified.
- **[5/10]** (quick win) Document the seven undocumented runners (hermes, copilot, crush, grok, qwen, pi + RPC variants) in `org-runtime.md` §2 — as a security audit, not just a listing (see the policy item). Known gap to fold in: the Hermes runner parses only ```tool_call fences (`hermes-runner.ts:16-17,196`), so Hermes's native tool-call syntax doesn't round-trip and a role emitting it silently loses tool use (CHANGELOG 2.10.30 "known follow-up").
- **[5/10]** Vercel and Hermes runner cost tracking is token-only (`cost_usd: 0`, `vercel-runner.ts:167`; Hermes adopted the same precedent); a maintained vendor price table would let budget enforcement work in dollars for 15+ vendors.

## MCP Tools & Knowledge Graph Memory (part of `@monoes/monomindcli`)

This subsystem is the MCP surface `@monomind/cli` exposes to Claude Code and other MCP clients (`packages/@monomind/cli/src/mcp-tools/**`, 25 domain modules registered from `mcp-tools/index.ts`), alongside two distinct knowledge stores it fronts: the "memory knowledge graph" (`memory-kg.ts`, Cognee-style entity/relation triplets) and the "Second Brain" document index (`document-pipeline.ts`), which a rule-based router (`query-router.ts`) fuses together with rules and pattern memories behind the single `knowledge_search` tool.

### Achieved Milestones
- 25 MCP tool modules registered via a flat re-export in `mcp-tools/index.ts`, backing three transports (stdio `bin/mcp-server.js` — hand-rolled JSON-RPC, the primary path; HTTP and WebSocket via `@monoes/mcp`) and a 9-subcommand `monomind mcp` CLI (start/stop/status/health/restart/tools/toggle/exec/logs).
- ~236 tools are registered (208 `inputSchema` definitions + 28 hooks tools); `listMCPTools` advertises the ~67-tool `CORE_TOOL_CATEGORIES` roster by default and everything under `MONOMIND_MCP_FULL=1` or `monomind_tool_search` (`mcp-client.ts:120-135`). Monograph alone contributes 46 (19 default, 27 behind `MONOGRAPH_MCP_ADVANCED=1`).
- Measured latency (local, Node 26): `initialize` 22.6 ms incl. spawn; `tools/list` 0.4 ms median; `monograph_query` 6.9 ms, `monograph_suggest` 14.2 ms, `knowledge_search` 4.7 ms, `memory_kg_search` 0.9 ms medians — all inside the < 100 ms target; first calls are the exception (see Future).
- `knowledge_search` implements a real multi-surface retrieval router: it picks among `chunks`, `kg`, `rules`, and `memory` surfaces, fuses results by reciprocal rank, and reports per-surface status (requested/executed/failed/empty/unsupported) plus the retrieval method used.
- Second Brain document pipeline (`document-pipeline.ts`, 1116 lines): multi-format ingestion (Office/PDF/text), heading-aware chunking (3200 chars, 400 overlap, respects code fences), SHA-256 content-hash dedup, superseded-version tracking, and Open Knowledge Format (OKF) export/import.
- Global + project "brain" merge: `knowledge_search`'s `store: 'project'|'global'|'all'` queries the personal cross-project brain and the project brain together (project wins ties).
- Memory knowledge graph (`memory-kg.ts`, 3147 lines): `kgIngest`, `kgIngestRules`, `kgSearch`, `kgGlossary`, `kgRollback` (per-`originRef` undo), `kgPromote`, `kgConsolidateCandidates`, `kgStats`, `kgIntegrityCheck`, index status/rebuild — with deterministic entity-key normalization, a 0.78 dedup threshold for rules, an adjacency index (no O(n²) scans), and **org-scoped partitioning** (`KgScope` suffixes every namespace `kg:nodes:org:<org>`, `memory-kg.ts:13-21`; crossing into the shared graph is the explicit `kgPromote` op).
- `knowledge_ingest`/`knowledge_search`/`knowledge_remove` resolve against `getProjectRoot()` rather than process `cwd` (a fixed bug where one brain could silently split into two) and validate paths with realpath containment (`knowledge-tools.ts:23,410`).
- A "Documents" dashboard tab (`localhost:4242`) hardened against DNS-rebinding (Host-header allowlist) and symlink path-escape — documented post-ship security fixes.
- A self-adversarial eval harness (`knowledge/eval/harness.ts`) keeps retrieval-quality claims honest: asserts k ≪ corpus size, runs random/BM25 baselines to detect a vacuous eval, drops near-verbatim query/target pairs, blocks network access during query time.

### Future Milestones

## Cross-Cutting Themes (scored)

Threads that recur across several packages — the highest-leverage places to look first.

1. **[10/10] Hooks must never break or slow the host session.** Generated hooks run on every tool call in Claude Code; today one un-`unref`'d timer costs ~5 s per Bash/Write/Edit (measured), the pre-write gate can fail open on a 3 s timeout, and every external bug report (#42, #58, #236, #129) is a hook that broke a session. Guard the class: bare-shell executability smoke test, per-handler latency regression test (< 200 ms with empty stdin), settings timeouts ≥ internal timers, fail-open wrappers for enrichment hooks only, fail-closed gates in their own hook entries.
