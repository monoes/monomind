# Monomind — Project Milestones

A full-monorepo review, package by package: what's actually shipped ("Achieved Milestones," verified against the real source/docs/tests) and what's worth doing next ("Future Milestones," each carrying an impact score). This is an ideation stepping stone, not a committed roadmap — add, re-score, and prune freely.

**Revision 4 (2026-09-16, 01:40 CEST).** Revision 1 was a 13-agent inventory; revision 2 re-verified everything and added scores; revision 3 (round 1 of an hourly loop) added the Monoswarm and Dashboard sections. This revision is round 2: five lenses — org-runtime runner-by-runner, checkpoint/resume end-to-end, statusline/token accounting reconciled against real transcripts, agent/skill/command content, and the knowledge layer measured with real ingests and searches. ## How to read the scores

Every future item starts with `[N/10]` — **impact on users and on the project's core promise**, not effort. `(quick win)` marks items that look like under a day of work.

| Score | Meaning |
|---|---|
| **10** | Fixes something currently broken or unsafe for most users, or unlocks the core promise |
| **8–9** | Major capability, reliability, or trust gain for a large share of users |
| **6–7** | Solid improvement with moderate reach, or high value at low effort |
| **4–5** | Nice-to-have, niche audience, or hygiene with some user-visible benefit |
| **1–3** | Cosmetic / internal tidiness, low user impact |
| **0** | Not worth doing or unsupported by evidence → removed |

## monomind (umbrella) (`monomind` v2.10.30)

`monomind` is the umbrella package published on npm — the thing `npm install -g monomind` actually installs. It ships zero code of its own: `bin/cli.js` is a pure forwarding shim that locates `@monoes/monomindcli` on disk and `import()`s its bin — deliberately, because publishing the CLI payload from both packages once caused a ~27 MB double-publish and a version-lockstep bug. The repo root also hosts the pnpm workspace, release/version-integrity scripts, CI workflows, top-level docs, and the crash reporter's entry point.

### Achieved Milestones
- Umbrella/CLI split with a dependency-resolution shim robust across nested, hoisted, global, and pnpm-linked layouts and the CLI's `exports` map gating.
- Lockstep version + double-publish prevention via `scripts/check-publish-versions.mjs` (`prepublishOnly`): root == CLI version, `workspace:*` enforced, `npm publish` blocked, `EOVERRIDE` caught early.
- Doc-count drift automation (`scripts/generate-doc-counts.mjs`) with `--check` in CI — two counters only (`workers`, `root-skills`); CLAUDE.md's headline figures ("29 hook subcommands", "8 workers", "66+ tools") are unmarked and wrong or unverified.
- Git hooks auto-activation (`scripts/install-hooks.mjs`) — inside this repo only.
- Three-workflow CI suite (`tests.yml` root + 9-package Linux + 5-package Windows matrix; `publish-smoke-test.yml` with a 4-case behaviour suite; `pages.yml`). No lint, typecheck, or coverage gate in any workflow.
- pnpm workspace with 28 security-driven `overrides` floors; `pnpm audit`: 0 vulnerabilities across 542 dependencies. 17 concept docs (10 with stale version pins, 7 with none). Apache 2.0.
- Outbound egress audited: code, documents, memory, and prompts stay local unless the user configures a provider or clicks "Upload org". Default-on egress: a 24 h-throttled npm update check on every CLI run (`index.ts:132`), `doctor`'s `npm view`, and the crash reporter. Opt-in: HuggingFace model download on first embedding use, NVD/OSV for `security cve`, monoes.me org upload, provider APIs, `security redteam --target`.
- Active release cadence (2.2.0 Org Runtime v2; 2.8–2.9 swarm-driven review-fix releases; 2.10.x runner robustness). Backlog: 8 open / 176 closed; the 7 external reports cluster on generated hooks breaking the host session and install/native-module breakage.

### Future Milestones
- **[8/10]** (quick win) Make the tarball smoke test import every `dist/src/commands/*.js` and `mcp-tools/**/*.js` entry point and run an `initialize → tools/list` stdio handshake against the installed package — four "uninstallable release" incidents (#130/#148 `workspace:*` twice; #16–#21 missing `zod`; #17/#46/#47 missing monobrowse) got past the current suite, and #36/#39 were install-time MCP stdio failures it never exercises.
- **[7/10]** (quick win) Fix the privacy claim: `package.json:4` "no data leaves your machine" and README:99 "never to a monoes-controlled server" are false as written (npm on every run, `doctor`'s `npm view`, public crash issues, monoes.me upload). Reword to "your code, documents and memory stay local; opt-in and maintenance calls are listed in Trust & Security", complete that table, ship `monomind doctor --network`.
- **[7/10]** (quick win) Lint, typecheck, and coverage-baseline gates in `tests.yml`: `pnpm lint` fails today (45 biome errors / 5 warnings across 1,313 files); no workflow runs biome or `tsc --noEmit`; all 8 vitest configs have coverage off with no thresholds.
- **[6/10]** Windows CI for `cli`/`monograph`/`memory` via the win32-x64 prebuilds tree-sitter*/better-sqlite3 already ship (`--ignore-scripts` + `prebuild-install`); run `tests/hooks` on Windows; a job that executes every generated hook command with `{}` on stdin (the generator emits only `sh -c` wrappers).
- **[5/10]** (quick win) Fold the root publish and `git tag`/`push --tags` into `cli/scripts/publish.sh` (newest tag v2.10.26 vs 2.10.30 shipped).
- **[4/10]** (quick win) `pnpm test:all` omits monobrowse and monofence-ai. `~/.monomind` growth: 160 MB, 89 project dirs incl. `agent-ops-test-*` fixtures left by the test suite — tests should use a temp `MONOMIND_HOME`; add `doctor --prune-home`.

## Org Runtime v2 (part of `@monoes/monomindcli`)

Org Runtime v2 is a daemon-coordinated system for running autonomous multi-agent "organizations" — role-based teams of live, provider-backed AI sessions (a boss plus specialist roles) that communicate over async mailboxes, persist resumable state via checkpoints, and can be driven by interchangeable LLM backends, with fault tolerance, cross-org/cross-process messaging, and a full audit trail (`bus.jsonl`).

### Achieved Milestones
- `OrgDaemon` lifecycle (`orgrt/daemon.ts`, ~1076 lines): `startOrg`/`stopOrg`/`deliver`/`resumeOrg`, lazy role spawning, atomic `spawning` guard.
- 14 runtime ids over 14 files (`agent-runner.ts` = Claude SDK, plus 13 `*-runner.ts`: opencode, kimicode, codex, antigravity, vercel (15 vendors incl. Gemini), hermes, copilot, crush, grok, qwen, qwen-rpc, pi, pi-rpc). Six are documented in `org-runtime.md`. Per the round-2 matrix: `maxTurns` is honored by claude and vercel only; provider-session resume works for 8 runners (SDK, codex, opencode, vercel, kimicode, qwen, antigravity, grok) and not for 6 (copilot, crush, pi, pi-rpc, qwen-rpc, hermes); usage/cost is real for 6 of 14 (claude and opencode return USD; codex/antigravity/qwen/pi return tokens; copilot and crush report zero, grok's field names are guessed, kimicode's come from a timestamp-filtered wire file).
- "Fence Protocol" (`tool-fence.ts`) rendering org tools as markdown and parsing tool calls back out of plain text for the 12 runners without native tool-calling; `MAX_TOOL_ROUNDS` = 10 bounds org-tool rounds.
- Per-role provider/runtime resolution (role > org > `MONOMIND_RUNTIME`), mixed-runtime orgs.
- Checkpoint/resume (`checkpoint.ts`, `checkpoint-ops.ts`): captured on stop/crash only; every `runtime.json` write is tmp+rename (`json-file.ts:76-84`) and a truncated file yields a clear error; v1→v2 migration, checksum and unknown-version validation tested. What survives resume (round-2 matrix): unconsumed mailbox queues, usage incl. retired usage, generations/respawn counts, role overrides, the task DAG, gates and `ask_human` questions (side files). What doesn't: the in-flight message, worktrees, pending approvals, conversation state on 6 runners (scrollback is captured but never re-injected).
- Four workspace isolation modes (`repo`, `isolated`, `worktree`, `worktree-per-role`).
- Per-role `PolicyEngine` (tool allow/deny, file globs with realpath symlink handling, web-domain allowlists, budgets, git levels) — enforced through the Claude SDK `canUseTool` hook only; subprocess runners' native tools are not policed.
- Fault tolerance: bounded boss restarts, per-role circuit breaker, idle watchdog, stale-PID detection, serve lock, atomic `runtime.json`, orphan SDK reaping. `OrgBus` append-only JSONL with 10 event types; `StateDetector` for live per-role activity.
- Cross-org/cross-process messaging (mailboxes, HTTP broker, offline queuing, `autoWake()`, `org inbox` for SSH delivery); `ask_human`, `org_gate`, `org_task*` DAG, `OrgScheduler`; org-scoped KG memory; ~130+ role skill prompts.
- Tests: every runner has a dedicated test file (13 under `__tests__/orgrt/`, 4,319 lines, plus `src/__tests__/{agent,codex,antigravity,vercel}-runner.test.ts`) — parser-fixture and fake-child tests; none exercise real subprocess semantics (process groups, pipe inheritance, argv limits) or a shared timeout/exit contract. 60+ orgrt test files overall; there is no fake runner (`MONOMIND_RUNTIME` selects only real runners).

### Future Milestones
- **[9/10]** Enforce role policy on subprocess runners — and stop leaking the daemon's environment into them. `PolicyEngine.decide()` runs only through the SDK `canUseTool` hook; the Codex runner launches with sandbox mode `danger-full-access` (`codex-runner.ts:392`), the Antigravity runner passes its permission-bypass flag (`:367`), the Qwen runner `--yolo` (`:346`). Compounding it, `resolveProviderEnv` starts from a full copy of `process.env` (`provider.ts:14-17`; `subscription` deletes only the three ANTHROPIC vars, `codex`/`antigravity` kinds delete nothing) and every runner spreads `{...process.env, ...args.env}` again (codex `:400`, antigravity `:374`, qwen `:351`, hermes `:270`, copilot `:320`, crush `:318`, grok `:385`, pi `:356`, pi-rpc `:252`, qwen-rpc `:212`, kimi `:294`, claude `:189`) — so a Codex role runs with `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GITHUB_TOKEN`, `AWS_*` and an unsandboxed native shell. Plan: map policy → native sandbox flags where supported, OS sandbox otherwise; build the child env from an allowlist (PATH/HOME/LANG/TERM/XDG_*/TMPDIR + a `passEnv` field in `RUNNER_SPECS` + an explicit role `env_passthrough`); `org validate` warns and `org run` requires `--accept-unsandboxed` when a role's policy is narrower than its runner can enforce; publish the enforcement matrix; scrub-on-spawn test per runner.
- **[8/10]** Checkpoint fidelity — "resumable" doesn't hold. (a) `finishStop` force-removes shared and per-role worktrees (`daemon.ts:2294-2318`) and `startOrgInner` removes/re-adds the shared worktree unconditionally (`:685-704`); `spawnRoleIncarnation` reuses a worktree only when the same process still has the slot (`:1346-1350`), never true on resume — every stop→resume in `worktree`/`worktree-per-role` mode destroys uncommitted role work. (b) `Mailbox.serialize()` copies `queue` only (`mailbox.ts:202-209`), `inFlight` is never serialized, and `finishStop` captures (`:2158`) before it aborts the turn (`:2182`) — the message being processed is silently dropped (lost entirely on the 6 non-resuming runners). (c) Pending approvals live in `approvals.json` but the daemon's Map starts empty on resume, so `org approve` 404s; `clearApprovalsForFreshStart` (`approvals.ts:70`) documents the ghost-approval problem and has zero callers. Plan: skip worktree removal on `stopped`/`crashed` (or stash/commit to `org/<run>/<role>`), record `worktreePath` in `RoleCheckpoint` and re-attach on resume; `serialize()` returns `inFlight` and capture prepends it to the queue; persist/rehydrate pending approvals; tests: write a file in a role worktree → stop → resume → assert it survives; push a message, let the session shift it, stop → assert it's in the checkpoint. Only then does the periodic checkpoint below pay off.
- **[8/10]** (quick win) `org serve` shuts down as a crash: its SIGTERM/SIGINT/SIGHUP handler calls `persistCrashStateAll()` then `process.exit` (`org.ts:1313-1325`), while `org run`'s handler resolves into `daemon.stopAll()` for a graceful checkpoint (`:609-616`). A systemd stop or terminal close of the long-lived daemon always lands in `status: crashed, closedBy: crash-handler` with the in-flight turn lost and worktrees orphaned. `await daemon.stopAll({ drainMs })` with a ~10 s hard-exit fallback.
- **[8/10]** (quick win) Vercel roles fragment the org bus per token — `vercel-runner.ts:137-143` yields an `assistant` message for every `text-delta` with no `extras.includePartialMessages` gate (every other streaming runner gates: `agent-runner.ts:170`, `antigravity-runner.ts:441`, `opencode-runner.ts:107`, `pi-rpc-runner.ts:237`, `qwen-rpc-runner.ts:204`), and `session.ts` treats each as a complete turn — `bus.emit({type:'chat'})` + `onOutput` per fragment (`:712-716`), `StateDetector` regexes run on fragments (a mid-sentence "done" flips state, `state-detector.ts:14`), `CONTEXT_LIMIT_RE` can never match across deltas. One line per token in `bus.jsonl`/scrollback/dashboard for every Gemini/GLM/DeepSeek/OpenAI-via-vercel role. Accumulate per step and yield once (mirror antigravity's `flushText`); contract test "one assistant message per step when `includePartialMessages` is unset".
- **[7/10]** Abort and timeout kill only the direct child. Every kill path is `child.kill()` on the direct `ChildProcess` (`agent-runner.ts:66-93` `killOnAbort` and its eight copies) — no `detached: true`, no `process.kill(-pid)` anywhere in orgrt except `forwarder.ts:96`. Verified with the built Codex runner and a fake `codex` that traps TERM and backgrounds `sleep 20`: abort fired at 1.5 s, the shell was SIGKILLed at ~6.5 s, but `run()` only threw at 20.0 s when the grandchild released stdout — and the error read "codex exec failed (exit 1)", indistinguishable from a crash. A role that launched a dev server or `npm test` keeps it running after `org stop`. Spawn `detached: true`, kill the process group, `child.stdout.destroy()` on SIGKILL so the read loop unblocks, tag abort-caused failures (`err.aborted`) so the daemon's crash/backoff path can tell them apart; add the grandchild case to `runner-abort.test.ts` (today a fake EventEmitter child).
- **[7/10]** Per-cwd session stores bleed across roles: pi and pi-rpc pass `--session-dir join(args.cwd, '.monomind-pi-session')` (`pi-runner.ts:221`, `pi-rpc-runner.ts:239`) and rely on "resume the latest session in the dir"; crush relies on `--continue` = most-recent session per cwd (`crush-runner.ts:17-27,313`). Under `workspace: 'repo'` two pi (or two crush) roles resume each other's conversations, a boss restart can resume a specialist's session, and `.monomind-pi-session/` is written into the user's repo. Vercel already keys by `MONOMIND_ORG_DIR`/`MONOMIND_ROLE_ID` (`session.ts:577-582`) — do the same (`<orgDir>/runners/<roleId>/`) for pi's `--session-dir` and crush's `--data-dir`; two-roles-one-cwd test.
- **[7/10]** Six runners restart cold on resume and nothing says so: `args.resume` is unused in copilot/crush/pi/pi-rpc/qwen-rpc and impossible in hermes (`hermes-runner.ts:25-37`); scrollback (500 lines) is captured (`daemon.ts:1426-1427`) but never fed into any prompt (no `scrollback` in `session.ts`). Inject a bounded prior-transcript block from `scrollback` into the first resumed prompt for runners lacking resume; emit a `resume-context-lost` audit per role so the dashboard shows it.
- **[7/10]** Liveness and runner-contract harness.
