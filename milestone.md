## monomind (umbrella) (`monomind` v2.10.30)

`monomind` is the umbrella package published on npm — the thing `npm install -g monomind` actually installs. It ships zero code of its own: `bin/cli.js` is a pure forwarding shim that locates `@monoes/monomindcli` (the real CLI, in `packages/@monomind/cli`) on disk via `require.resolve.paths()` and `import()`s its bin. It's deliberately structured this way because publishing the CLI payload from both packages once caused a ~27MB double-publish and a two-package version lockstep bug — the shim's own header comment documents the incident as the reason it must stay code-free. The root of the repo also hosts all repo-wide tooling: the pnpm workspace definition, release/version-integrity scripts, CI workflows, and top-level docs (README, CHANGELOG, LICENSE).

### Achieved Milestones
- Umbrella/CLI split with a dependency-resolution shim (`bin/cli.js`) robust across nested, hoisted, global, and pnpm-linked `node_modules` layouts, and against the CLI's `exports` map gating (falls back to filesystem resolution rather than `require.resolve()` on the package specifier, since older published CLI versions reject that).
- Lockstep version + double-publish prevention via `scripts/check-publish-versions.mjs`, run as `prepublishOnly`: enforces root version == CLI version, enforces the `workspace:*` protocol (not a hand-written literal) on the CLI dependency pin, blocks `npm publish` in favor of `pnpm publish` (npm can't rewrite `workspace:*`, so it would ship an uninstallable tarball), and catches npm's `overrides`-vs-direct-dependency conflict (`EOVERRIDE`) before it only surfaces for end users.
- Doc-count drift automation (`scripts/generate-doc-counts.mjs`) — computes counts (background workers, root skills) from source of truth and substitutes them into `<!-- doc-count:NAME -->` markers across README/CLAUDE.md/doc/*, with a `--check` mode wired into CI/prepublish so stale docs fail the build instead of silently drifting (built after a real incident where "8 workers" vs "15 workers" disagreed across five docs).
- Git hooks auto-activation (`scripts/install-hooks.mjs`, run via `prepare`) — points `core.hooksPath` at `.githooks/` (which has `pre-commit` secret scanning and `commit-msg` hooks) on every install, fails silently outside a git repo so it's safe as a dependency install too.
- Three-workflow CI suite: `tests.yml` runs a root job plus a 9-package Linux matrix and a 5-package Windows matrix (each gap in Windows coverage explicitly documented rather than silently skipped); `publish-smoke-test.yml` does pre-publish tarball-install smoke tests (PR-triggered), post-publish registry smoke tests (daily cron, since git tags aren't reliably pushed on release), and a 4-case "published behaviour" regression suite asserting specific past incidents (init data-loss, secret-gate fail-open, security-worker false-clean, status fabricated-zeros) stay fixed; `pages.yml` deploys `doc/` to GitHub Pages on push to main.
- pnpm workspace spans `packages`, `packages/@monomind/*`, `packages/@monoes/*`, `packages/plugins/*`, and `packages/monofence-ai`, with root-level `overrides` (security-driven version floors for hono, axios, esbuild, protobufjs, sharp, etc.) and `onlyBuiltDependencies` scoping native builds to tree-sitter/better-sqlite3.
- `doc/concepts/` holds 17 concept docs: antigravity, codex, documents-dashboard, hooks, kimicode, local-llm-providers, mcp-server, memory, monobrowse, monodesign, monograph, monoswarm, opencode, org-runtime, routing, security, statusline.
- Apache 2.0 licensed (confirmed in `LICENSE`), consistent with README's "use it however you want" claim.
- CHANGELOG (1300+ lines) shows an active, fast-moving release cadence — dozens of patch releases across Aug–Sep 2026 alone — with recognizable eras: 2.2.0 baseline (Org Runtime v2 SDK daemon), 2.8–2.9 "comprehensive review-fix" releases driven by multi-agent review swarms (2.9.0: 7-agent swarm found/fixed 28 issues across security/robustness/performance in one release, including a command-injection fix and dashboard binding-to-0.0.0.0 fix), and the current 2.10.x stream focused on agent-runner robustness (Hermes/Codex/OpenCode runner parity, streaming gating) and `doctor`/diagnostics accuracy fixes.

### Future Milestones (Ideas)
- No automated CHANGELOG generation — entries are hand-written per release; a `scripts/*` tool that drafts CHANGELOG sections from conventional commits or PR labels could reduce the manual burden visible in the current cadence.
- `check-publish-versions.mjs` and `generate-doc-counts.mjs` are both hand-rolled point solutions; as more cross-package invariants accumulate (e.g. worker counts, doc counts, version pins), a small internal "repo invariants" runner that registers checks declaratively could reduce duplicate CLI-arg/`--check` plumbing.
- Windows CI explicitly excludes `cli`, `monograph`, and `memory` (native module / node-gyp VS-detection issues) — closing that gap, if the underlying node-gyp/VS runner issue ever gets fixed, would give the umbrella package's most important consumer (the actual CLI) real Windows test coverage (currently only tarball install/smoke-tested cross-platform, not unit tested).
- `publish-smoke-test.yml`'s "behaviour" suite is a hand-curated list of 4 past-regression assertions — a lightweight, documented process for turning every future P0/P1 postmortem into a new case here (rather than relying on someone remembering to add one) would keep the ratchet effect it's clearly designed around.
- The registry smoke test runs daily by cron specifically because tagging is decoupled from publishing; automating tag creation as part of the publish flow itself would remove the need for the schedule-based workaround (would also make `push: tags: v*` a reliable release signal again).

## Org Runtime v2 (part of `@monoes/monomindcli`)

Org Runtime v2 is a daemon-coordinated system for running autonomous multi-agent "organizations" — role-based teams of live, provider-backed AI sessions (a boss plus specialist roles) that communicate over async mailboxes, persist resumable state via checkpoints, and can be driven by any of eight interchangeable LLM backends. It exists to let a single `monomind org` config file describe a durable, budget-bounded, human-supervisable agent team rather than a one-shot scripted agent loop — with fault tolerance (crash/restart, idle watchdog, circuit breakers), cross-org and cross-process messaging, and a full audit trail (`bus.jsonl`) for every message, tool call, and state transition.

### Achieved Milestones
- `OrgDaemon` lifecycle (`orgrt/daemon.ts`, ~1076 lines) covering `startOrg`/`stopOrg`/`deliver`/`resumeOrg`, with lazy role spawning (boss spawns immediately, specialists spawn on first mailbox message) and an atomic `spawning` guard against duplicate spawns.
- Eight interchangeable `AgentRunner` backends behind one interface: Claude (default, `@anthropic-ai/claude-agent-sdk`), Opencode, KimiCode, Codex (ChatGPT subscription), Antigravity (Google AI Pro/Ultra), Vercel AI SDK (15 vendors + OpenAI-compatible escape hatch), plus Copilot, Crush, Grok, Qwen and Pi runners present as additional `*-runner.ts` files.
- A "Fence Protocol" (`tool-fence.ts`) that renders org tools as markdown in the system prompt and parses tool calls back out of plain assistant text for runners without native tool-calling (opencode/kimi/codex/antigravity), including tolerant parsing of malformed trailing JSON.
- Per-role provider/runtime resolution with three-level precedence (role `runtime` > org-level `runtime` > `MONOMIND_RUNTIME` env), enabling mixed-runtime orgs (e.g., a Claude coordinator delegating to opencode workers).
- Checkpoint/resume system (`checkpoint.ts`, `checkpoint-ops.ts`) with 24h TTL, checksum validation, per-role mailbox queues, token/cost tracking, session IDs, and a bounded scrollback ring buffer (500-line default) restored on resume.
- Four workspace isolation modes: `repo`, `isolated`, `worktree` (shared git worktree), and `worktree-per-role` (one `git worktree add --detach` per non-boss role), all cleaned up on stop.
- Per-role `PolicyEngine` enforcing tool allow/deny lists, file read/write glob scopes, web-domain allowlists, per-role token budgets, and git access levels (`none`/`read`/`commit`/`push`).
- Fault tolerance: boss crash recovery with bounded restarts (`MAX_BOSS_RESTARTS=2`, backoff `[10s, 30s]`) before transitioning to a `crashed` state; configurable `circuit_breaker` that trips a role's mailbox after N consecutive session failures; idle watchdog (default 10 min, up to 3 nudges before stop).
- `OrgBus` append-only JSONL event log with in-process fan-out across 10 event types (message/xorg/tool/asset/chat/status/audit/usage/question/gate) plus disk replay via `readHistory()`.
- `StateDetector` infers live per-role activity (`idle`/`working`/`tool-call`/`blocked`/`error`/`completed`) from the raw SDK message stream, emitting `status` bus events on every transition.
- Cross-org and cross-process messaging: intra-org mailbox delivery, in-process cross-org lookup, HTTP broker-based cross-process delivery (`broker.ts`, filesystem registry with 20s heartbeat / 90s staleness), and offline queuing with `autoWake()`.
- Human-in-the-loop primitives: `ask_human` tool with live/offline-queued answer delivery, and `org_gate` hard-blocking approval checkpoints for irreversible actions.
- `org_task`/`org_task_done`/`org_tasks` dependency-DAG task tracking (`task-dag.ts`) with auto-dispatch of ready tasks to assignees.
- `OrgScheduler` for `org serve` scheduled runs, accepting `"15m"/"2h"/"45s"` interval strings, with catch-up-run coalescing and its own resume-clock phasing.
- Cross-run knowledge-graph memory per org (`org_recall`/`org_remember`/`org_learn`) plus optional Second Brain `knowledge_search` integration.
- ~130+ predefined role skill prompts under `orgrt/role-skills/` covering coordinator, dev, QA, security, marketing, finance, and game-dev archetypes, ready to assign to org roles.
- Broad test coverage (60+ files in `__tests__/orgrt/`) spanning checkpoint/resume, respawn, budget accounting, mailbox draining, circuit breakers, cross-process delivery, scheduler restarts, and per-runner adapter tests.

### Future Milestones (Ideas)
- Fix SSH-federated cross-org dispatch (`remote.ts`): `deliverRemote()` shells out to `npx monomind org inbox <name> --json`, but `inbox` isn't a registered `org` subcommand, so remote hosts reject it — connectivity checks (`pingRemote()`) work, but actual message delivery over SSH does not complete end to end.
- No `GeminiAgentRunner` exists — `gemini` is currently only a provider *env* kind (sets `GEMINI_API_KEY`) layered on top of another runner; a native Gemini CLI/SDK runner would close this gap, especially with Antigravity positioned as Google's replacement path (Gemini CLI consumer-OAuth sunsets 2026-06-18).
- Several runner backends (Copilot, Crush, Grok, Qwen/Qwen-RPC, Pi/Pi-RPC) exist as source + tests but aren't documented in `org-runtime.md` alongside the six documented runners — worth auditing for parity/completeness and folding into the doc.
- Vercel-runner cost tracking is token-only (`cost_usd: 0` always) since the Vercel AI SDK doesn't return USD pricing — a maintained vendor price table would let budget enforcement work in dollars, not just tokens, for those 15+ vendors.
- `stale_base_threshold` and `prechecks` are best-effort/silent-skip when git or an upstream branch is unavailable — could be hardened into an explicit warning/report surface rather than silent skipping.
- Optional-dependency runners (opencode, Vercel vendor packages) fail only at runtime with an actionable install message — a `monomind org doctor`-style preflight that checks installed optional deps per configured role before `org run` would catch misconfiguration earlier.

## MCP Tools & Knowledge Graph Memory (part of `@monoes/monomindcli`)

This subsystem is the MCP surface `@monomind/cli` exposes to Claude Code and other MCP clients (`packages/@monomind/cli/src/mcp-tools/**`, 25 domain modules registered from `mcp-tools/index.ts` — agent, analyze, autopilot, browser, claims, config, embeddings, github, graphify, guidance, hooks, knowledge, memory, monograph, monomind, monoswarm, performance, platforms, security, session, system, task, terminal, transfer — plus the `monograph/` submodule split across 8 files), alongside two distinct knowledge stores it fronts: the "memory knowledge graph" (`memory-kg.ts`, Cognee-style entity/relation triplets) and the "Second Brain" document index (`document-pipeline.ts`), which a rule-based router (`query-router.ts`) fuses together with rules and pattern memories behind the single `knowledge_search` tool.

### Achieved Milestones
- 25 MCP tool modules registered via a flat re-export in `mcp-tools/index.ts`, backing three transports (stdio `bin/mcp-server.js`, HTTP, WebSocket) and a 9-subcommand `monomind mcp` CLI (start/stop/status/health/restart/tools/toggle/exec/logs).
- Monograph alone contributes ~15+ documented tools (`monograph_build/watch/query/stats/health/god_nodes/get_node/shortest_path/...`) split into a default set and an advanced-gated set, per `doc/concepts/monograph.md`.
- `knowledge_search` implements a real multi-surface retrieval router: it picks among `chunks` (document excerpts), `kg` (memory graph), `rules`, and `memory` (pattern store) surfaces, fuses results by reciprocal rank, and reports per-surface status (requested/executed/failed/empty/unsupported) plus the actual retrieval method used — not just a flat vector search.
- Second Brain document pipeline (`document-pipeline.ts`, 1116 lines): multi-format ingestion (Office/PDF/text via `cap-documents.ts`), heading-aware chunking (3200 chars, 400 overlap, snaps to markdown headings and respects code fences), SHA-256 content-hash dedup, superseded-version tracking, and Open Knowledge Format (OKF) export/import (YAML frontmatter + `index.md` manifest) for portability.
- Global + project "brain" merge is implemented, not aspirational: `knowledge_search`'s `store: 'project'|'global'|'all'` param queries the personal cross-project brain and project brain together (project wins ties); `store: 'global'` deliberately excludes the KG/rules/pattern surfaces since those are project-scoped.
- Memory knowledge graph (`memory-kg.ts`, 3147 lines) is a full CRUD+ops surface: `kgIngest`, `kgIngestRules`, `kgSearch`, `kgGlossary`, `kgRollback` (per-`originRef` undo), `kgPromote`, `kgConsolidateCandidates`, `kgStats`, `kgReferenceEdges`, `kgIndexStatus`/`kgRebuildIndex`, `kgIntegrityCheck` — exposed as `memory_kg_ingest/search/rollback/stats` MCP tools, with deterministic entity-key normalization and a 0.78 dedup threshold for rules.
- `knowledge_ingest`/`knowledge_search`/`knowledge_remove` correctly resolve ingestion and search against `getProjectRoot()` rather than process `cwd` — a fixed bug (documented inline) where directory-ingest metadata could otherwise diverge from file-ingest/search and silently split one brain into two.
- A "Documents" dashboard tab (`localhost:4242`) surfaces mastermind-generated markdown across projects with two read-only routes, hardened against DNS-rebinding (Host-header allowlist) and symlink path-escape (`fs.realpathSync` containment check) — both documented as post-ship security fixes, not just design intentions.
- A self-adversarial eval harness (`knowledge/eval/harness.ts`, "the Second Brain scoreboard") exists to keep retrieval-quality claims honest: it asserts k stays a small fraction of corpus size, runs random/BM25 baselines to detect a vacuous eval, drops near-verbatim query/target pairs, blocks network access during query time, and rebuilds a pinned eval store per run.

### Future Milestones (Ideas)
- No automatic entity extraction from ingested documents into the memory knowledge graph — `document-pipeline.ts` never calls `kgIngest`, so a document's claims only enter the KG via a separate, manual `memory_kg_ingest` step; wiring an optional auto-extract-on-ingest path would close a real gap between "indexed" and "known."
- Three graph/knowledge-shaped stores exist in parallel and are explicitly *not* synchronized: the Monograph code graph, the memory knowledge graph (`kg:nodes`/`kg:edges`), and the Memory Palace's separate temporal triples (`.monomind/palace/kg.json`) — consolidating or at least cross-linking these (even just a shared entity-id scheme) would reduce the "which graph has the fact I'm looking for" confusion the docs currently have to call out.
- The memory KG's `kg:nodes`/`kg:edges`/`rules` namespaces are fixed strings per store with no org-scoped partitioning, so multiple orgs rooted at the same project silently share one graph — an opt-in namespacing scheme would let multi-org setups isolate or federate knowledge deliberately instead of by accident.
- `monograph_query` is documented as one-hop neighbor-expansion reranking rather than iterative PageRank — a genuinely deeper multi-hop ranking mode (opt-in, given the cost) could improve recall on architecturally distant but relevant nodes.
- The 25-module MCP tool surface has no single generated reference (the "66+ tools" figure in CLAUDE.md is asserted, not derived); a `monomind mcp tools --json` schema dump checked into docs would make the actual current tool/param inventory verifiable instead of trusted by convention.

## Init System & Multi-Platform Integration (part of `@monoes/monomindcli`)

The init system (`packages/@monomind/cli/src/init/`) scaffolds a project for five coding agent platforms — Claude Code, Antigravity (Gemini CLI), OpenCode, Kimi Code, and Codex — from one `executor.ts` orchestration pass, with `default`/`minimal`/`full` presets, an interactive wizard, per-platform "opt-in" flags, and an `init upgrade` path that refreshes an existing install's helpers/skills/agents without clobbering user data.

### Achieved Milestones
- Five wired platform targets (Claude, Antigravity/Gemini, OpenCode, Kimi Code, Codex), each with its own generator (`claudemd-generator.ts`, `geminimd-generator.ts`, `opencode-generator.ts`, `kimi-generator.ts`, `codex-generator.ts`) and writer (`write-claude.ts`, `write-antigravity.ts`, `write-opencode.ts`, `write-kimicode.ts`, `write-codex.ts`) producing instructions files, settings/MCP config, skills, commands, agents, and statusline per platform's native format.
- `monomind init --target <platform>` runs a single-system mode; plain `monomind init` runs all five; legacy per-platform boolean flags (`--opencode`, `--kimicode`, `--codex`) remain aliases for `--target`, per the doc/concepts pages.
- A separate, broader `platform-adapters/registry.ts` catalogs 16 platform IDs total (claude, gemini, cursor, vscode, copilot, opencode, aider, kiro, trae, openclaw, droid, antigravity, hermes, codex, kimi, zed) with per-capability support levels (`native`/`cli_fallback`/`unsupported`) across instructions/skills/mcp/commands/agents/hooks/status/lifecycle/permissions — a superset of what `executor.ts`'s five hardcoded targets actually wire up.
- Additive, non-destructive design: opencode/kimicode/codex artifact generation is opt-in (`components.opencode/kimicode/codex` default `false`) so standard `monomind init` output is unchanged; each platform writes into its own isolated directory (`.gemini/`, `opencode.json`+`.opencode/`, `.kimi-code/`, `.codex/config.toml`) and never touches another platform's files.
- Shared cross-platform surface: `.agents/shared_instructions.md` (via `shared-instructions-generator.ts`) plus `SKILL.md`-shaped skills are reused verbatim by OpenCode and Kimi Code rather than reimplemented per platform.
- Security gate parity per platform: OpenCode gets a `tool.execute.before` plugin, Kimi Code gets a `PreToolUse` hook bridge, both wrapping the same pre-bash/pre-write gate handlers Claude Code hooks use natively.
- Statusline propagation beyond Claude: the `.claude/helpers/statusline.cjs` implementation is mirrored/wired into Antigravity's `.gemini/settings.json`, Kimi Code's `~/.kimi-code/tui.toml` (only if the user's global Kimi config already exists — no unsolicited global writes), while OpenCode substitutes an on-demand `/monomind-status` command since it has no persistent statusbar hook.
- Three presets (`DEFAULT_INIT_OPTIONS`, `MINIMAL_INIT_OPTIONS`, `FULL_INIT_OPTIONS` in `types.ts`) plus an interactive wizard (`init-wizard.ts`, `select`/`multiSelect`/`confirm` prompts) covering preset choice, hooks, topology, memory backend, neural/self-learning, embeddings, governance gates, and document ingestion.
- `monomind init upgrade` (`upgrade.ts`, `executeUpgrade`/`executeUpgradeWithMissing`) refreshes helpers/metrics on an existing install and, with `--add-missing`, backfills missing skills/agents/commands — without deleting or overwriting user customizations (skip-if-exists semantics documented per-platform, e.g. Kimi/OpenCode never clobber a hand-written `AGENTS.md`).
- Non-fatal, best-effort auxiliary steps folded into `executeInit`: directory capability scanning + Second Brain document seeding, background Monograph code-graph build (with lock-file coordination against the session-start hook to avoid SQLite contention), and a post-init `doctor --install` pass — all individually skippable (`--no-install`) and reported via `result.skipped` rather than failing the whole init.
- Project self-registration into `~/.monomind-projects.json` on every init (worktrees under `.worktrees` explicitly excluded) so `init upgrade --all` can rediscover projects without a filesystem scan.
- As of this review's session: `monomind init` / `init --force` (including under `--minimal`) and `init --wizard` now unconditionally force-rebuild the Monograph code graph, decoupled from the `components.graphify` component flag (which still separately controls whether the ongoing `graphify-freshen.cjs` auto-refresh hook is installed); the `initKnowledgeGraph` build call now passes `{ force: true }` explicitly. Scoped narrow subcommands (`init skills`, `init hooks`) are unaffected.

### Future Milestones (Ideas)
- Close the gap between the 16-platform `platform-adapters/registry.ts` catalog and the 5 platforms `executor.ts` actually drives — Cursor, VS Code, Copilot, Aider, Kiro, Trae, OpenClaw, Droid, Hermes, and Zed are modeled with capability/support-level data but have no `write-*.ts`/generator or `--target` wiring yet, so registry entries look "supported" without an init path.
- Most registry entries beyond Claude/Gemini are `cli_fallback` or `unsupported` for several capabilities (e.g. `gemini` has `agents: unsupported`) — no doc equivalent to `doc/concepts/{antigravity,opencode,kimicode,codex}.md` exists yet for those partially-modeled platforms, so support levels aren't user-facing.
- OpenCode has no persistent statusbar equivalent (`/monomind-status` is pull, not push) — the docs flag `experimental.chat.system.transform` as a possible fix but explicitly disabled by default over per-turn token cost; a lighter-weight version could close that parity gap.
- `init.ts` carries a fair amount of accumulated flag-handling nuance (target vs. platform vs. legacy boolean flags, `--watch`/`--no-watch` vs `--start-all`/`--no-start-all` precedence) that could be consolidated as the platform list grows, to avoid the flag surface scaling linearly with each new adapter.

## CLI Commands: Diagnostics, Security, Hooks & Ops (part of `@monoes/monomindcli`)

This covers the operational, diagnostic, and security command surface of the `monomind` CLI: `doctor`, `security` (scan/cve/audit/secrets/defend/redteam), `performance`, the `hooks` subsystem (28+ subcommands and 9 background workers), `agent`, `task`, `session`, `monoswarm`, `memory` (12 subcommands), `config`, `status`, `providers`, `guidance`, `completions`, and the inlined `input-guards.ts` validation layer.

### Achieved Milestones
- `doctor` runs 28+ named health-check categories (`--component`) spanning environment (Node/npm/git/disk/build tools), project config, memory DB + knowledge graph freshness, MCP servers, API keys, monograph index freshness, agent registry, gitignore coverage, guidance gates, memory proficiency, worker-metrics freshness, and security-audit findings, with `--fix` auto-remediation for a subset (stale helpers, gitignore coverage, AppleDouble sidecars, monoes tooling).
- `security scan` performs real filesystem secret scanning (Stripe/OpenAI/AWS/GitHub/Slack key patterns, hardcoded passwords) with an explicit `ScanCoverage` model that tracks unreadable dirs/files, depth-truncated dirs, and oversized (>1MB) skipped files — so a clean result can be distinguished from an incomplete scan — and can export findings as SARIF.
- `security cve` checks/lists known CVEs with severity filtering, JSON output, and a `--no-cache` fresh-fetch option.
- `security audit` is a real audit-trail reader/writer (`--action list|log|export|clear`), supports `--follow` tailing and substring filtering by source/decision/tool/reason, and `--action export` writes the full trail to a file.
- `security defend` and its underlying detection engine (`doc/concepts/security.md`) run a multi-stage local pipeline — 64KB resource bound, allowlist bypass, Unicode/homoglyph/leetspeak/base64 evasion normalization, 50+ regex-based threat patterns across 9 threat classes, multi-turn escalation tracking, and post-hoc output scanning for PII leakage and prompt echo — claimed sub-10ms per scan, no data leaves the machine.
- `security redteam` lists a bundled library of adversarial test prompts (injection, alternate-persona, adversarial, and PII-probing categories, max 5 prompts/category) for manual review by default; passing `--target` switches to live mode, POSTing each prompt and evaluating the response via the same detection engine's `scanOutput()` — genuinely live, not just a listing.
- `input-guards.ts` (394 lines, replaces the deleted `@monomind/security` package) provides typed validation for string/number/path/url/orgName, a symlink-aware path-traversal guard (`realOrResolved` walks to the longest existing ancestor and realpath's it, closing a bypass where a symlink is lexically inside cwd but physically escapes it), URL protocol allowlisting (http/https only), an org-name regex validator, MCP-specific control-character/NUL rejection, and a git-ref safety validator.
- `performance` provides `benchmark` (suite selection, iterations, warmup), `profile` (target/type/duration), `metrics` (timeframe/component filter), and `bottleneck` (component + depth) — described as real measurements, not simulated.

## @monoes/memory (`@monoes/memory` v1.0.17)

Standalone, publishable memory backend package underneath monomind's CLI — a unified `IMemoryBackend` over pluggable SQLite drivers (native `better-sqlite3` primary, `sql.js` WASM fallback for platforms without a native build), with a pure-JS HNSW ANN index, document chunking/retrieval, and cross-session checkpointing. It's consumed by `@monomind/cli` as the canonical backend behind `monomind memory` commands and MCP memory tools; the CLI layers its own richer schema (SONA/EWC pattern learning, trajectories) on top rather than inside this package.

### Achieved Milestones
- Unified `SqlBackend` (`src/sql-backend.ts`) replaced two drifted ~1,780-line better-sqlite3/sql.js implementations with one behavior layer over a `SqlDriver` abstraction, closing real bugs (differing tag-filter ANY/ALL semantics, missing tag validation, a sql.js crash on missing rows).
- Size-gated HNSW fast path is real and matches the documented default: `ANN_THRESHOLD` (`src/sql-backend.ts:87-91`) defaults to 5000 active embedded entries, overridable via `MONOMIND_HNSW_THRESHOLD`; below it, search stays brute-force cosine (cheaper per the code's own comment), above it a pure-JS `HNSWIndex` graph is built once per `(dimensions, count, maxUpdatedAt)` fingerprint and reused/persisted.
- `forceBuildAnnIndex()` gives an explicit `memory search --build-hnsw` escape hatch to build the index regardless of threshold.
- HNSW index (`src/hnsw-index.ts`, ~1000 lines) implements real optimizations: binary min/max heaps for O(log n) candidate selection, pre-normalized (L2) vectors for O(1) cosine distance, and serialize/deserialize for on-disk caching.
- Per the project's own doc (`doc/concepts/memory.md:135`), when installed this package's HNSW index is tried *first* by the CLI on every semantic search, not merely as a fallback for a broken native binding — falling through to brute-force SQLite only when HNSW returns nothing.
- `better-sqlite3 ^12.0.0` is a mandatory (not optional) dependency as of 1.0.14+, fixing a real prior failure mode where Node version mismatches silently fell back to sql.js against a schema that didn't support it (documented in `doc/concepts/memory.md`'s troubleshooting section).
- LanceDB is genuinely and fully gone — confirmed in code (`src/types.ts:5`) and docs: replaced by SQLite in July 2026; a `lancedb`-named directory is kept only for back-compat path resolution and now holds SQLite data.
- `MonoswarmCheckpointer` (`src/checkpointer.ts`) provides crash-recoverable, append-only JSON-lines swarm checkpointing with an O(1) in-memory cache for the "latest" lookup (avoiding an O(n) full-file reparse per incremental save).
- Supporting infra is solid and tested: `QueryBuilder`, `CacheManager`, `PromptVersionStore`, a document chunker/`KnowledgeStore`/`KnowledgeRetriever`, and a legacy-source `MemoryMigrator` — backed by ~13 test files including dedicated `ann-search`, `backend-conformance`, and `sql-schema` suites.
- Package correctly ships as alpha-tagged (`publishConfig.tag: "alpha"`) with a `prepublishOnly` guard that fails the build if required exports (`SQLiteBackend`, `SqlJsBackend`, `HNSWIndex`, `CacheManager`, `QueryBuilder`, `MonoswarmCheckpointer`) go missing.

### Future Milestones (Ideas)
- **The "L2, L1, min-max, z-score" normalization and "Hyperbolic embeddings — Poincare ball model" claims made in `packages/@monomind/cli/CLAUDE.md` are aspirational, not real**: the only normalization implemented anywhere in this package (or in `@monomind/cli`) is L2/cosine (`src/math-utils.ts`, `src/hnsw-index.ts:821`). No L1, min-max, z-score, or hyperbolic/Poincare code exists in either package — worth either wiring the types to real logic here or correcting the docs so they don't imply this package does adaptive/hyperbolic learning it doesn't.
- This package's own embedding generation is a toy hash function (`createHashEmbedding` in `src/math-utils.ts`) used only as a fallback/test vector generator — real dense embeddings (ONNX via `@xenova/transformers`) are generated entirely in `@monomind/cli`, outside this package's scope; the package only stores/indexes vectors it's handed via the injected `EmbeddingGenerator` callback. Worth documenting explicitly so users don't expect semantic embeddings out-of-the-box from `@monoes/memory` alone.
- No on-disk ANN cache directory is wired up in the base `SqlBackend` (`getAnnCacheDir()` returns `null` unconditionally per `src/sql-backend.ts:97-99`) — every process restart above the 5000-entry threshold rebuilds the HNSW graph from scratch unless a subclass overrides this; a default persistent cache path would remove that rebuild cost for long-running or CLI-invoked processes.
- Given the package is still alpha (1.0.x) and does real vector search work, an obvious next milestone is benchmarking/publishing actual measured HNSW speedups against the brute-force path (the code cites 150x-12,500x targets in `PERFORMANCE_TARGETS`, `src/types.ts:757-761`, but these read as targets, not measured results — worth verifying if not already load-bearing).

## @monoes/monograph (`@monoes/monograph` v1.6.4)

Monograph is monomind's in-process, SQLite-backed codebase knowledge graph engine — it parses source files with tree-sitter WASM grammars (no native builds) plus a regex fallback for a few more languages, extracts symbols and structural relationships into a SQLite graph, runs derived graph analyses (blast radius, community detection, god-node/surprise detection), and tracks index freshness against Git. Both the CLI's `mcp__monomind__monograph_*` MCP tools and the CLI's session-start hooks (auto-build/auto-suggest) depend on it directly; it also ships a standalone LSP server as a separate export.

### Achieved Milestones
- 14 bundled tree-sitter WASM grammars (c, cpp, c_sharp, dart, go, java, kotlin, php, python, ruby, rust, swift, typescript, tsx) covering 25 file extensions end to end, plus a regex-based fallback extractor for 5 more languages (Scala, Lua, Zig, PowerShell, Elixir) — 30 extensions total, no native compilation required at install time.
- Full 18-phase build pipeline (`src/pipeline/orchestrator.ts`, `src/pipeline/phases/*`): scan → structure → parse → variables → markdown → routes → tools → orm → cross-file → bridge-resolver → mro → wildcard-synthesis → import-resolver → scope-resolution → god-nodes → communities → processes → surprises → suggest, plus framework-detect and git-churn analysis feeding into the same graph.
- Cross-file relationship resolution: import/module resolution, bridge-adapter resolution, Python-style MRO computation, wildcard-import synthesis, and scope-aware symbol resolution are each their own dedicated phase rather than folded into parsing.
- File-scoped build lock (`orchestrator.ts` `acquireBuildLock`) with dead-PID and 30-minute-stale reclaim, so concurrent builds serialize instead of corrupting the SQLite DB.
- 5-state explicit freshness model (`src/staleness/git-staleness.ts`): `fresh | stale | building | partial | unknown`, distinguishing "proven up to date" from "could not check" — plus dirty-worktree detection (via `git status`) layered on top of the git-commit-hash comparison, so uncommitted edits are surfaced rather than silently reported fresh.
- SQLite storage layer (`src/storage/db.ts` + `schema.ts`) with `nodes`/`edges`/`communities`/`index_meta`/`file_cache` tables, FTS5 trigram full-text search with auto-sync triggers, and a `schema_version` table for migrations.
- Blast-radius/ripple-impact analysis via BFS graph traversal with exponential depth decay, formatted directly into LLM-ready markdown reports.
- Louvain community detection (graphology-communities-louvain) plus a separate Leiden implementation (`phases/leiden.ts`) for graph clustering.
- 46 total MCP tools registered (`mcp-tools/monograph/index.ts`) — 19 exposed by default, 27 more gated behind `MONOGRAPH_MCP_ADVANCED=1` — covering build/watch, BM25 query with one-hop neighbor-expansion reranking, god-nodes, shortest-path, community inspection, surprises, suggest, staleness, deep context assembly, impact, and a subset-Cypher query interface.
- A live file-system watcher (`src/watch/watcher.ts`, chokidar-based) with a 20-file incremental-vs-full-rebuild threshold and a 60s idle deferred full-rebuild to reconcile drift.
- Standalone LSP server (`./lsp` export, `src/lsp/`) with 6 dedicated test suites (server, hover, code-lens, code-actions, diagnostics, diagnostics-ext) — a genuinely separate capability from the MCP tool suite, self-hostable via `monomind monograph lsp`.

### Future Milestones (Ideas)
- **No real incremental build exists yet.** `buildIncrementalAsync()` in `orchestrator.ts` is currently a documented no-op shortcut: it calls `buildAsync(..., { incremental: false })`, i.e. it always does a full rebuild. The code's own comment explains why: a prior partial implementation only re-parsed changed files without rerunning relationship resolution or derived analyses (communities, god-nodes, etc.), silently dropping edges — so correctness was chosen over speed until a real incremental path (tracking changed files' dependents, recomputing only their relationships, invalidating only affected derived analyses) is built and proven equivalent to a clean build. This is the single biggest architectural gap in the package.
- No language coverage for HTML/CSS or plain JS-only projects beyond what the TS/TSX grammar happens to parse — Vue is handled by isolating `<script>` blocks rather than a native Vue grammar; a dedicated web-template grammar (or Svelte/Astro support) is an open gap.
- The doc (`doc/concepts/monograph.md`) still headlines package version `v1.5.6` while `package.json` is at `1.6.4` — worth a doc refresh pass alongside whatever else changed in that version gap (the doc itself already flags its MCP tool list as a stale "15 selected examples" enumeration versus the real 46-tool registry).
- Freshness staleness detection (layer 1) is git-commit-based and explicitly documented as unable to determine staleness when git is unavailable (non-Git checkout, missing binary, shallow/detached HEAD) — it reports "not stale" in that case with no real evidence behind it. A non-git fallback (e.g. mtime-based) would close a real blind spot for non-git-tracked or vendored code.
- The three memory/graph subsystems in the repo (monograph's SQLite graph, the CLI's separate pattern-store memory, and the standalone HNSW fallback index) are explicitly not consolidated per project docs — monograph could be the natural convergence point if that consolidation is ever prioritized.

## @monoes/routing (`@monoes/routing` v1.0.4)

Small, dependency-free TypeScript package (`packages/@monomind/routing`) implementing the first two tiers of Monomind's task-to-agent routing cascade: a deterministic regex keyword pre-filter and a vector cosine-similarity matcher over per-agent route "centroids," plus an LLM-fallback classifier for low-confidence cases. It ships zero runtime dependencies and is consumed by `@monomind/cli`, which wires in the later tiers (SQLite/ReasoningBank augmentation, outcome ledger) and an optional real embedding model — this package itself never trains or learns anything.

### Achieved Milestones
- Tier-1 `KeywordPreFilter` with 30+ first-match-wins regex rules (`src/keyword-pre-filter.ts`) covering security/CVE, test files, Docker/K8s/Terraform/GitHub Actions, git subcommands, Solidity, ZK proofs, MCP, React Native, iOS/Swift, Android/Kotlin, embedded/firmware, Salesforce, game engines (Unity/Unreal/Godot/Blender), SEO, supply chain, GraphQL, and databases — plus support for prepending custom higher-priority rules.
- Deliberate false-positive guards on ambiguous English words (`swift`, `unity`, `embedded`, `apex`, `blender`) using bidirectional lookahead/lookbehind context windows rather than bare substring matches.
- Tier-2 `RouteLayer` (`src/route-layer.ts`) that averages per-route utterances into centroids (`computeCentroid`/`cosineSimilarity` in `cosine.ts`), supports host-supplied precomputed centroids to skip runtime recomputation, a configurable global threshold override, and a `debug` mode returning all route scores.
- Two swappable encoders (`encoder.ts`): `LocalEncoder`, a genuinely hash-based (MD5 unigram+bigram, SHA-256-keyed, 2000-entry LRU cache, L2-normalized, 256-D) deterministic pseudo-embedding with **no ML model** — confirms this package is keyword/hash-based, not neural by itself; and `HNSWEncoder`, a thin wrapper that uses a host-injected real embedding function (e.g. a HuggingFace transformers pipeline supplied by the CLI) and falls back to `LocalEncoder` when none is provided.
- `LLMFallbackRouter` (`src/llm-fallback.ts`) that builds a capability-index + top-3 candidate-hint prompt, validates the LLM's returned slug against a strict pattern and the known route list, and explicitly distinguishes a genuine LLM match (`method: 'llm_fallback'`, confidence 0.85) from a degraded/failed fallback (`method: 'semantic_degraded'`, raw cosine score) — a correctness fix so failed fallbacks can't masquerade as successful ones.
- 9 curated route domains (`src/routes/*.route.ts`, ~1000 lines total: core, security, engineering, testing, design, marketing, product, specialized, game-dev) aggregated via `ALL_ROUTES`.
- Full unit test coverage mirroring every module (`__tests__/`: route-layer, keyword-pre-filter, llm-fallback, encoder, cosine, capability-index, classify-prompt), including LRU-eviction, hash-determinism, and precomputed-centroid performance tests.
- `doc/concepts/routing.md` explicitly documents (and this review confirms by reading the source) that "Neural"/Tier-3 labeling refers only to embedding-similarity lookups against a stored pattern set, not a trained model — there is no RL, Q-table, or learned state-action values anywhere in the routing subsystem.

### Future Milestones (Ideas)
- The package still has no bundled real embedding model of its own — semantic quality entirely depends on whatever the host (CLI) injects via `embeddingGenerator`/`HNSWEncoder`; a lightweight optional bundled embedder (even a small quantized model) would let `@monoes/routing` work well standalone, outside the monomind CLI.
- Complexity scoring (length/keyword heuristics) and the outcome-tracking ledger currently live entirely in `@monomind/cli` (`hooks-routing.ts`, `monovector/route-outcomes.ts`) rather than in this package — pulling core scoring/measurement logic into `@monoes/routing` would give it a single source of truth and make it usable independent of the CLI.
- The ambiguous-word disambiguation pattern list (swift/unity/embedded/apex/blender) is hand-maintained; a small golden-set of true/false-positive phrases would guard against regressions as new keyword rules are added.
- No route-coverage or precision/recall benchmark ships in-package against a labeled task-description corpus — only structural/unit tests exist; a small golden-set eval (measuring keyword vs. semantic vs. fallback accuracy) would give routers a regression signal when rules or thresholds change.
- `RouteLayerConfig.centroids` requires the caller to guarantee "same embedder" — there's no runtime dimensionality/embedder-identity check, so a mismatched centroid set would silently produce meaningless cosine scores rather than failing fast.

- Documented three-layer crash/hang recovery (`doc/concepts/monobrowse.md` §5): a 30s default timeout on every CDP send (`DEFAULT_CDP_SEND_TIMEOUT_MS` in `cdp.ts`) with immediate flush on `Target.targetCrashed`/`Target.targetDestroyed`; best-effort `Browser.close`/PID-kill cleanup on Ctrl-C/SIGTERM; and a persisted-PID (`active-port.json`) recovery path so `monomind browse close` can kill an orphaned Chrome process from a later, fresh CLI invocation after a `SIGKILL`.

### Future Milestones (Ideas)
- The recovery doc still ends in a manual last resort (`ps aux | grep remote-debugging-port` + manual kill) for a stale/deleted PID file — a periodic reaper or `browse doctor` subcommand that scans for orphaned `--remote-debugging-port` processes tied to `.monomind/monobrowse/` state could close that final gap.
- Only 6 platform adapters exist (linkedin, instagram, x, gemini, google, microsoft); broader adapter coverage (e.g. GitHub, Slack, generic OAuth/SSO detection) would reduce how often agents hit the headed-fallback flow.
- The dashboard's playbook Builder (drag-and-drop action composer) is UI-only right now per the code structure — exposing playbook import/export or versioning via the CLI would let playbooks be checked into a repo rather than living only in the dashboard's local state.
- No adapter test coverage beyond `adapters.test.ts` for basic login detection; CAPTCHA-wall detection heuristics (password field / reCAPTCHA iframe sniffing) are a likely source of false positives/negatives worth a dedicated fixture suite as more sites are added.
- `monodesign`'s CLI engine still carries an optional Puppeteer dependency fallback for live visual audits — fully migrating that fallback onto monobrowse would let the repo drop its last residual Puppeteer dependency.

## @monoes/monodesign (`@monoes/monodesign` v1.2.6)

Monomind's frontend design intelligence engine: a rule-based anti-pattern detector, deterministic auto-fix codemod, and a curated OKLCH color-seed library, exposed both as MCP tools (`monodesign_detect`, `monodesign_fix`, `monodesign_palette`) and as a CLI (`monomind design detect/fix/palette`), plus a large `skill/` knowledge base (26 commands, 60+ reference docs) that backs the `/monodesign` agent for broader UX/brand/critique work beyond mechanical detection.

### Achieved Milestones
- 51 catalogued anti-pattern rules in `cli/engine/registry/antipatterns.mjs` spanning layout (nested cards, monotonous spacing, cramped padding), typography (overused/single font, flat type hierarchy, gradient text, oversized H1, crushed letter spacing), color/contrast (AI-generic palette, cream/beige palette, gray-on-color, low contrast), motion (bounce easing, layout-property transitions), and copy tells (em-dash overuse, marketing buzzwords, aphoristic cadence).
- Four-tier detection engine architecture: `engines/regex` (text-pattern scan), `engines/static-html` (DOM/CSS-cascade aware via `css-select`/`css-tree`/`domutils`/`htmlparser2`), `engines/browser` (live URL detection via a pluggable browser driver), and `engines/visual` (pixel-level contrast checking via screenshots) — the browser/visual tiers only activate when a driver is available, so static analysis works standalone.
- Deterministic browser driver seam (`cli/engine/engines/browser/drivers.mjs`) that prefers `@monoes/monobrowse` (monorepo's native CDP client, no bundled Chromium needed) and falls back to `puppeteer`, selectable via `MONODESIGN_BROWSER_DRIVER`; both are `optionalDependencies` so the core detector has no hard browser dependency.
- Recent reliability hardening on that driver seam: each detection launch now gets its own throwaway `userDataDir` (commit `645579717`, "give each detection launch its own Chrome profile dir") to stop concurrent launches on the same port from colliding on a shared profile, plus waits for CDP port bind/release rather than just unreachability — addressing flaky concurrent/CI detection runs.
- `monodesign_detect` runs fully in-process (`engine.detectText`/`engine.walkDir`, no subprocess spawn) per `packages/@monomind/cli/src/mcp-tools/monodesign-tools.ts`; `monodesign_fix` spawns the bundled CLI codemod with a 2-minute bound and defaults to `dry_run: true` so nothing is written without explicit opt-in.
- Curated OKLCH palette library (129 hand-picked seeds in `skill/scripts/palette.mjs`) with inverse-hue-frequency weighting for roughly even hue-zone distribution, and deterministic selection via SHA-256 hash of a `from:` key (e.g. product name) or direct `id: "seed-NNN"` lookup — intentionally emits no hex, only `oklch()`.
- Inline waiver support: detection honors `monodesign-disable*` comments in scanned source so teams can suppress specific findings per-line/file.
- Recently fixed packaging bugs (`9ae687e5e`, `c2a8dfa6e`): package entry previously pointed at `.ts` source instead of compiled `dist/`, and `npm publish` wasn't rebuilding `dist/` — both now fixed with a `prepublishOnly` build step, at v1.2.6.
- 50 test files under `tests/` including fixture-driven anti-pattern corpora for real framework output shapes (Next.js CSS-in-JS, Next.js CSS modules, Next.js Tailwind, Vite) plus multi-file scenarios, critique snapshots, and a `live-e2e` suite.
- Broad `skill/` surface beyond mechanical detection: 26 slash-style commands (`audit`, `critique`, `harden`, `polish`, `distill`, `colorize`, `typeset`, `animate`, `layout`, `adapt`, `onboard`, `teach`, `live`, etc.) each backed by a reference doc, plus a `live/` browser-iteration toolchain (`live-browser.js`, `live-inject.mjs`, `live-poll.mjs`, `live-commit-manual-edits.mjs`) for applying and tracking manual UI edits in a running app session.

### Future Milestones (Ideas)
- The visual/contrast detection tier depends on an external browser driver (monobrowse or puppeteer); a documented "static-only, no browser available" degradation report (which rules silently skip) would help agents/CI know what coverage they're actually getting.
- No component-framework-aware detection yet beyond static HTML/CSS output — rules operate on rendered/text HTML, so JSX/Vue-SFC-native source isn't scanned directly (fixture coverage confirms only *built* Next/Vite output is tested, not source files).
- `monodesign_fix`'s 2-minute subprocess bound and dry-run default suggest large-codebase fix runs could time out silently; a progress/partial-result reporting mode for bigger `--target` trees would help agents track big auto-fix sweeps.
- The anti-pattern registry (51 rules) has no visible severity/confidence weighting surfaced through the MCP tool description — grouping or prioritizing findings (e.g., accessibility-blocking vs. purely stylistic) could make `monodesign_detect` output more actionable for agents triaging large diffs.
- Given the recent string of driver-profile/CDP-timing bugs (three fix commits in quick succession: `645579717`, `ca1ef4c98`, `ae489a6fc`), a stress/soak test for concurrent detection launches against monobrowse would help confirm the class of flake is actually closed rather than incrementally patched.
- The 129-seed palette library is curated but static; no mechanism for extending or auditing seed distribution (e.g., a CLI/report command showing current hue-frequency balance) is evident.

## monofence-ai (`monofence-ai` v1.0.2)

monofence-ai is monomind's standalone AI-manipulation defense package — a regex/heuristic engine that detects attempts to manipulate an LLM's behavior via crafted input (instruction overrides, alternate-persona framing, obfuscation/evasion, multi-turn escalation) and PII, plus scans LLM outputs for leakage and policy violations. It ships as its own npm package (`packages/monofence-ai`) with domain-driven structure (`domain/entities`, `domain/services`, `hooks/`) and is consumed both as a library (`import { isSafe, createMonoDefence } from 'monofence-ai'`) and via the monomind CLI's `security defend`/`security redteam` commands and its own hook registration API.

### Achieved Milestones
- Core `MonoDefence` API shipped: `detect()` (async, full scan), `quickScan()` (sync, sub-ms), `hasPII()`, `scanOutput()`, allowlist bypass, `getStats()`, plus module-level `isSafe()`/`checkThreats()` singleton helpers.
- 50+ regex-based detection patterns implemented in `threat-detection-service.ts` (549 lines), grouped into technique families: attempts to override prior instructions, adopt an unrestricted alternate persona, fabricate system-prompt context, obfuscate payloads via encoding, and frame a request as hypothetical or educational to bypass policy.
- Evasion detection (`evasion-detector.ts`, 231 lines) normalizes obfuscated input before pattern matching: NFKC normalization, homoglyph substitution (Cyrillic/Greek/IPA/fullwidth lookalikes), leetspeak expansion, punctuation-separator collapsing, spaced-char collapsing, zero-width character stripping, and base64 payload detection/decoding (with printable-byte-ratio heuristics to avoid false positives on JWTs/SHAs).
- Multi-turn context tracking (`context-tracker.ts`, 147 lines): a 4-state escalation machine (`clean → probing → escalating → attack`) with cumulative threat scoring, a confidence floor to avoid low-confidence FPs driving escalation, idle-based decay (30 min default), and gradual per-turn de-escalation after 3 consecutive clean turns.
- Output scanning (`output-scanner.ts`, 131 lines) checks LLM responses for 4 signals: PII leakage (email/phone/SSN/credit-card regexes), prompt-echo via trigram Jaccard similarity (≥0.4 threshold), policy-violation patterns (unsafe-instruction phrasing), and disclaimer-then-comply contradiction detection.
- Self-learning module (`threat-learning-service.ts`, 519 lines) with an in-memory vector store, learned-pattern storage, and mitigation-strategy tracking (`learnFromDetection`, `searchSimilarThreats`, `getBestMitigation`), opt-in via `enableLearning`.
- Hook wiring (`security-hook.ts`, 209 lines): registers Critical-priority `pre-task` and `pre-command` hooks against any `@monoes/hooks`-compatible registry (duck-typed, no hard dependency), aborting execution when threat confidence ≥ 0.8.
- CLI integration verified: `monomind security defend -i/-f/--stats` scans arbitrary text/files for threats via dynamic `import('monofence-ai')` (`packages/@monomind/cli/src/commands/security-misc.ts`); `monomind security redteam --target <url>` POSTs a bundled library of adversarial test prompts to a live endpoint and evaluates the response with `scanOutput()` — a real live-execution red-team path, not just a static prompt listing (dry-run/listing is the default without `--target`).
- Test coverage exists (~1,230 lines across `__tests__/`), and the package builds/typechecks independently (`tsc`, `vitest`).

### Future Milestones (Ideas)
- Detection patterns are hand-authored regexes only — no ML/embedding-based classifier, so attacks worded outside the ~50 known patterns (paraphrases, novel phrasings) will slip through; a learned/semantic detection layer beyond the opt-in `ThreatLearningService` pattern-matching would close this gap.
- The redteam attack library caps at 5 prompts per category ("max 5 — that is all that exist" per the CLI help text) — a genuinely small library for a red-team tool; expanding it (or sourcing more broadly from established adversarial-prompt research) would materially improve coverage.
- `ThreatLearningService`'s vector store is in-memory only (`InMemoryVectorStore`) — learned patterns and mitigation effectiveness don't persist across process restarts unless a caller supplies a custom `VectorStore`; wiring a persistent backend (e.g. reusing `@monoes/memory`'s SQLite store) would make the "self-learning" claim durable.
- Homoglyph/leetspeak tables are fixed small maps (Cyrillic/Greek/IPA/fullwidth + basic leet substitutions) — broader Unicode confusable coverage (e.g. the full Unicode confusables database) would harden evasion detection against less common lookalike scripts.
- Output scanning's policy-violation and PII regexes are narrow (unsafe-instruction phrasing; email/phone/SSN/credit-card only) — no coverage for other sensitive-data classes (API keys/secrets are mentioned in the README's feature list but the `OutputScanner`'s `PII_PATTERNS` array itself only covers 4 types) or jurisdiction-specific PII formats.
- No rate-limiting or backpressure logic is evident for the `redteam --target` live-execution path, which POSTs a real attack library at a target endpoint — worth documenting/guarding for accidental misuse against production endpoints.

## Cross-Cutting Themes (Ideation Seeds)

A few threads recur across multiple package reviews above — likely the highest-leverage places to look first when picking a future milestone to pursue:

1. **Doc/code version drift.** `doc/concepts/mcp-server.md` cites `@monoes/mcp` as v1.0.1 (actual: 1.0.4); `doc/concepts/monograph.md` cites v1.5.6 (actual: 1.6.4); `@monoes/hooks`'s own `package.json` description says "8 workers" (actual: 9); `packages/@monomind/cli/CLAUDE.md` asserts memory-normalization and hyperbolic-embedding capabilities that don't exist in code. The repo already has doc-count-drift tooling (`scripts/generate-doc-counts.mjs`) for *some* of these — extending its scope, or a lighter "doc claims vs. code reality" linter, would catch this class of drift before it compounds further.
2. **Unconsolidated parallel graph/memory stores.** At least four separate graph-or-memory-shaped stores exist without a shared identity scheme: the Monograph code graph, the CLI's memory knowledge graph (`kg:nodes`/`kg:edges`), the Memory Palace's temporal triples, and `@monoes/memory`'s SQLite+HNSW store (with a separate pure-JS HNSW fallback). This is called out from multiple independent angles (MCP/knowledge review, monograph review, CLI-ops review) — a real opportunity for architectural consolidation.
3. **"Registered but not wired" gaps.** The platform-adapters registry claims 16 platforms but `init` only drives 5; `@monoes/mcp`'s `ConnectionPool` is fully built but never instantiated by its only caller; monograph's `buildIncrementalAsync()` exists as an API but is a full-rebuild shortcut under the hood. A recurring pattern worth a dedicated audit pass: places where the surface area looks bigger than what's actually reachable at runtime.
4. **Security/defense surfaces are real but narrow.** monofence-ai's regex-only detection, `security scan`'s 5-pattern secret scanner, and the 5-prompts-per-category redteam library are all functioning, live-tested systems — but each is explicitly narrow by pattern-count rather than ML/learned coverage. Broadening any of these (maintained signature sets, semantic detection layers, larger attack libraries) is lower-risk, well-scoped follow-up work.
5. **Windows/native-module coverage gap.** CI explicitly excludes `cli`, `monograph`, and `memory` from the Windows test matrix due to native module build issues — these are also three of the most heavily-used packages in the whole system.
