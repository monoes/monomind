# Monomind — Project Milestones

A full-monorepo review, package by package: what's actually shipped ("Achieved Milestones," verified against the real source/docs/tests) and what's worth doing next ("Future Milestones," each carrying an impact score). This is an ideation stepping stone, not a committed roadmap — add, re-score, and prune freely.

**Revision 3 (2026-09-16, 00:45 CEST).** Revision 1 was a 13-agent inventory; revision 2 re-verified every item with a 10-agent swarm and added scores. This revision is round 1 of an hourly review-and-discovery loop (6 fresh lenses: monoswarm/agent/task/session tools, the 13 never-reviewed MCP tool modules, the privacy/egress promise, the dashboard, generated hook-script correctness, monograph parse/index accuracy). It adds two sections that had no coverage at all — **Monoswarm & Agent/Task/Session Stores** and **Dashboard (Neural Control Room)** — ~30 new items (one measured 10/10 and five 9/10s), and corrects three revision-2 claims.

## How to read the scores

Every future item starts with `[N/10]` — **impact on users and on the project's core promise**, not effort. `(quick win)` marks items that look like under a day of work.

| Score | Meaning |
|---|---|
| **10** | Fixes something currently broken or unsafe for most users, or unlocks the core promise |
| **8–9** | Major capability, reliability, or trust gain for a large share of users |
| **6–7** | Solid improvement with moderate reach, or high value at low effort |
| **4–5** | Nice-to-have, niche audience, or hygiene with some user-visible benefit |
| **1–3** | Cosmetic / internal tidiness, low user impact |
| **0** | Not worth doing or unsupported by evidence → removed |

## monomind (umbrella) (`monomind` v2.10.30)

`monomind` is the umbrella package published on npm — the thing `npm install -g monomind` actually installs. It ships zero code of its own: `bin/cli.js` is a pure forwarding shim that locates `@monoes/monomindcli` (the real CLI, in `packages/@monomind/cli`) on disk and `import()`s its bin — deliberately, because publishing the CLI payload from both packages once caused a ~27 MB double-publish and a version-lockstep bug. The repo root also hosts all repo-wide tooling: the pnpm workspace, release/version-integrity scripts, CI workflows, top-level docs, and the crash reporter's entry point.

### Achieved Milestones
- Umbrella/CLI split with a dependency-resolution shim robust across nested, hoisted, global, and pnpm-linked `node_modules` layouts and against the CLI's `exports` map gating.
- Lockstep version + double-publish prevention via `scripts/check-publish-versions.mjs` (`prepublishOnly`): root version == CLI version, `workspace:*` protocol enforced, `npm publish` blocked in favor of `pnpm publish`, npm `EOVERRIDE` conflicts caught early.
- Doc-count drift automation (`scripts/generate-doc-counts.mjs`) with `--check` in CI — but only two counters (`workers`, `root-skills`); the headline figures in CLAUDE.md ("29 hook subcommands", "8 background workers", "66+ tools") are unmarked and wrong or unverified.
- Git hooks auto-activation (`scripts/install-hooks.mjs` via `prepare`) — inside this repo only.
- Three-workflow CI suite (`tests.yml` root + 9-package Linux + 5-package Windows matrix; `publish-smoke-test.yml` pre/post-publish tarball smoke with a 4-case behaviour suite; `pages.yml`). No lint, typecheck, or coverage gate in any workflow.
- pnpm workspace with 28 security-driven `overrides` floors and `onlyBuiltDependencies` scoped to tree-sitter/better-sqlite3; `pnpm audit`: 0 vulnerabilities across 542 dependencies.
- 17 concept docs under `doc/concepts/` (10 with stale per-doc version pins, 7 with none). Apache 2.0 licensed.
- Outbound network egress audited (round 1): code, documents, memory, and prompts stay local unless the user configures a provider or clicks "Upload org" in the dashboard. Default-on egress is limited to a 24 h-throttled npm update check on every CLI run (`index.ts:132`, 5 s abort, off via `--no-update`/`MONOMIND_AUTO_UPDATE=false`/`CI`), `doctor`'s `npm view` version check, and the crash reporter (see CLI Commands). Opt-in: HuggingFace model download on first embedding use (~90 MB MiniLM), NVD/OSV for `security cve`, monoes.me for dashboard org upload, user-configured provider APIs, `security redteam --target`.
- CHANGELOG (1300+ lines) shows an active cadence with recognizable eras (2.2.0 Org Runtime v2; 2.8–2.9 swarm-driven review-fix releases; 2.10.x runner robustness). Backlog: 8 open / 176 closed issues; the 7 external reports cluster entirely on generated hooks breaking the host session and install/native-module breakage.

## Org Runtime v2 (part of `@monoes/monomindcli`)

Org Runtime v2 is a daemon-coordinated system for running autonomous multi-agent "organizations" — role-based teams of live, provider-backed AI sessions (a boss plus specialist roles) that communicate over async mailboxes, persist resumable state via checkpoints, and can be driven by interchangeable LLM backends, with fault tolerance, cross-org/cross-process messaging, and a full audit trail (`bus.jsonl`).

### Achieved Milestones
- `OrgDaemon` lifecycle (`orgrt/daemon.ts`, ~1076 lines): `startOrg`/`stopOrg`/`deliver`/`resumeOrg`, lazy role spawning, atomic `spawning` guard.
- 13 `AgentRunner` backend files behind one interface: Claude (default, SDK), Opencode, KimiCode, Codex, Antigravity, Vercel AI SDK (15 vendors incl. Gemini via `google`), Hermes, Copilot, Crush, Grok, Qwen (+RPC), Pi (+RPC). Six documented in `org-runtime.md`; seven not.
- "Fence Protocol" (`tool-fence.ts`) rendering org tools as markdown and parsing tool calls back out of plain text for runners without native tool-calling.
- Per-role provider/runtime resolution (role > org > `MONOMIND_RUNTIME`), mixed-runtime orgs.
- Checkpoint/resume (`checkpoint.ts`, `checkpoint-ops.ts`): 24 h TTL, checksums, per-role mailbox queues, token/cost tracking, bounded scrollback — captured on stop/crash only (see Future).
- Four workspace isolation modes (`repo`, `isolated`, `worktree`, `worktree-per-role`), cleaned up on stop.
- Per-role `PolicyEngine` (tool allow/deny, file globs with realpath symlink handling, web-domain allowlists, token budgets, git levels) — enforced through the Claude SDK `canUseTool` hook (`session.ts:586`, `policy.ts:206-260`). **For subprocess runners it covers only in-process org tools; the child CLI's native file/shell/web tools are not policed.**
- Fault tolerance: bounded boss restarts, per-role circuit breaker, idle watchdog, stale-PID detection, serve lock, atomic `runtime.json`, orphan SDK reaping.
- `OrgBus` append-only JSONL with in-process fan-out across 10 event types; `StateDetector` for live per-role activity.
- Cross-org and cross-process messaging (mailboxes, HTTP broker with heartbeat, offline queuing, `autoWake()`) and an `org inbox` subcommand (`org.ts:2337-2366`) that `remote.ts:66` shells to over SSH.
- Human-in-the-loop `ask_human` and hard-blocking `org_gate`; `org_task*` dependency-DAG tracking; `OrgScheduler` for `org serve`.
- Cross-run KG memory per org (`org_recall`/`org_remember`/`org_learn`, org-scoped via `KgScope`); ~130+ predefined role skill prompts.
- 60+ test files in `__tests__/orgrt/` — broad on daemon/checkpoint/budget/mailbox/scheduler, thin per runner (11 of 14 runners have ≤ 3 referencing test files).

### Future Milestones
- **[9/10]** Enforce role policy on subprocess runners. `PolicyEngine.decide()` runs only through the SDK `canUseTool` hook; the Codex runner launches with sandbox mode `danger-full-access` (`codex-runner.ts:392`), the Antigravity runner passes its permission-bypass flag (`antigravity-runner.ts:367`), the Qwen runner passes `--yolo` (`qwen-runner.ts:346`) — a role with `fileWrite: ['src/**']` and an empty `webAllow` gets full disk and network on those backends. Map policy → native sandbox flags where supported, run the child under an OS sandbox otherwise, make `org validate` warn and `org run` require `--accept-unsandboxed` when a role's policy is narrower than its runner can enforce, and publish an enforcement matrix per runner.
- **[7/10]** Liveness regression harness — the largest closed-issue cluster (~45: idle watchdog #168/#173/#175/#183/#194, approvals #135/#160/#213/#214, resume #140/#149; #204 alone took 13 commits; external #25) keeps re-breaking. `org run --simulate` with a fake runner asserting the three invariants (productive work continues / only real blockers stop / no infinite loop) in CI on every orgrt change, plus one parameterized runner contract test (stream parsing, exit-code → status, `includePartialMessages` gating, abort) with fake timers.
- **[7/10]** (quick win) The dashboard's "Upload org" (`ui/routes-monoes.mjs:318`) posts the raw `.monomind/orgs/<name>.json` to monoes.me, and `orgrt/types.ts:89,93` permit inline `apiKey`/`authToken`. Strip `apiKey`/`authToken`/`env` values and any `*_KEY`-shaped strings before upload, show a diff preview, and add a 15 s timeout to the fetches (none today).
- **[6/10]** (quick win) `run_config.prechecks` only execute for `org serve` (sole caller `org.ts:1354`); `org run` never runs them. `stale_base_threshold` promises "warn or refuse" (`daemon.ts:1072`) but can only emit an audit event.
- **[6/10]** Periodic checkpoints and bus rotation: `captureCheckpoint` runs only on stop/crash (`daemon.ts:2158,2356,2398`), so SIGKILL/OOM leaves nothing to resume; `bus.jsonl` is append-only forever and readers load the whole file. Debounced checkpoint (N events / 60 s, atomic) and a segmented bus rolled at ~50 MB.
- **[6/10]** (quick win) `org validate` checks schema only (`org-observe.ts:44`); call the existing `scanInstalled()` preflight (`runner-registry.ts:369`) per role runtime, and publish a per-runner verification ledger — #178/#181/#242/#243 exist because users can't tell which runtimes are verified.
- **[5/10]** (quick win) Document the seven undocumented runners in `org-runtime.md` §2 as a security audit; fold in that the Hermes runner parses only ```tool_call fences (`hermes-runner.ts:16-17,196`), so native Hermes tool calls silently lose tool use.

## MCP Tools & Knowledge Graph Memory (part of `@monoes/monomindcli`)

The MCP surface `@monomind/cli` exposes to Claude Code and other clients (`mcp-tools/**`, 25 modules), plus the two knowledge stores it fronts: the memory knowledge graph (`memory-kg.ts`) and the Second Brain document index (`document-pipeline.ts`), fused by `query-router.ts` behind `knowledge_search`.

### Achieved Milestones
- 25 modules; ~236 registered tools (208 `inputSchema` definitions + 28 hooks tools); `listMCPTools` advertises the ~67-tool `CORE_TOOL_CATEGORIES` roster by default, everything under `MONOMIND_MCP_FULL=1` / `monomind_tool_search` (`mcp-client.ts:120-135`). ## Monoswarm & Agent/Task/Session Stores (part of `@monoes/monomindcli`)

The "monoswarm" coordination feature — 13 `monoswarm_*` MCP tools, the `agent_*`/`task_*`/`session_*` tools, and the `monomind monoswarm|agent|task|session` CLI groups. Every tool in this area is JSON bookkeeping: `agent_spawn` starts no process, votes are tallied in-process, and **no code links monoswarm state to Claude Code's Agent/Task tool** — the "CLI coordinates, Task tool executes" rule in the generated CLAUDE.md is a prompt convention the model is asked to follow. ## Init System & Multi-Platform Integration (part of `@monoes/monomindcli`)

The init system (`packages/@monomind/cli/src/init/`) scaffolds a project for Claude Code and other agentic coding platforms from one `executor.ts` pass — presets, wizard, `init upgrade`, a 16-platform adapter registry — and generates the hook scripts (`.claude/helpers/*.cjs`) that then run on every tool call inside the host session. Because those hooks sit on the hottest path in the product, this section also owns hook latency, hook safety, and whether hook output actually reaches the model.

### Achieved Milestones
- Five fully-wired platform targets (Claude, Antigravity/Gemini, OpenCode, Kimi Code, Codex) with per-platform generators and writers; plain `monomind init` writes all of them.
- `platform-adapters/registry.ts` catalogs 16 platform IDs with per-capability support levels; `init --platform <id>` and `monomind platforms plan|install|upgrade|uninstall|doctor|docs` route every id through `installPlatform()`; `docs/platforms/compatibility.md` is generated from the registry and CI-checkable.

## Cross-Cutting Themes (scored)

1. **[10/10] Hooks must never break, slow, or silently no-op inside the host session.** Generated hooks run on every tool call: one un-`unref`'d timer costs ~5 s per Bash/Write/Edit (measured); the pre-write gate can fail open on four paths; the post-commit hook's `npx monomind@latest` hangs 70 s offline; and — the quiet half — the enrichment those hooks exist to provide never reaches the model by default (`MONOMIND_HOOK_QUIET=1`, plain stdout on tool hooks). Every external bug report (#42, #58, #236, #129) is a hook that broke a session. Guard the class: bare-shell executability smoke, per-handler latency test (< 200 ms), timeouts ≥ internal timers, `additionalContext` for tool-hook output, fail-open wrappers for enrichment only, fail-closed gates in their own hook entries.
2. **[9/10] Install and offline resilience.** Native-module ABI failures (#231, #219, #244), uninstallable tarballs (#130, #148, #16–#21, #17/#46/#47), Windows gaps, and `@latest` tag resolution on every MCP start account for the rest of external reports.
